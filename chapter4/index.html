第四章

正確的工作流程

你不會跟建築師說「幫我蓋房子」就等交屋。你會先看樣品屋、討論格局、看設計圖，最後才動工。跟 AI 做專案也一樣。

本章目錄
  1. 新手的做法 vs 正確的做法
  2. 第一步：先做 Demo（10 分鐘）
  3. 第二步：看著 Demo 確認邊界
  4. 第三步：規劃架構，先看計畫
  5. 第四步：正式開始寫
  6. 為什麼不能跳過第二步和第三步
  7. 蓋房子的完整流程
  8. 這章帶走什麼
  9. 跟 Claude 怎麼說

上一章講怎麼下指令：目標、邊界、情境，還有先講跟後講差在要不要打牆。這章講的是順序：同樣一句話，什麼時候說、先做哪一步。

簡單講就是三件事：先看樣子、先看計畫、再動手。下面一步一步拆開。

新手的做法 vs 正確的做法

絕大多數新手拿到 AI 工具，第一件事就是打一段話：「幫我做一個預約系統。」然後 AI 噴出 50 個檔案，你看不懂、改不動，最後砍掉重練。

新手的做法
你：「幫我做一個 CRM 系統。」

AI：（生成 50 個檔案、3 個資料表、
用了你沒聽過的框架、
加了你不需要的功能）

你：「等等，這不是我要的……」
你：「這個拿掉、那個改掉」
你：「為什麼改了 A 功能，B 壞了？」
你：「算了，砍掉重練。」

花了 3 小時 + 大量 Token = 什麼都沒得到
正確的做法
Step 1：Demo（10 分鐘）
Step 2：確認邊界（10 分鐘）
Step 3：規劃架構（20 分鐘，先看計畫）
Step 4：正式開始寫（一次一塊，省時省 Token）

花了 40 分鐘 + 少量 Token = 方向正確

CRM 是客戶關係管理（Customer Relationship Management），白話說就是「客戶資料和往來紀錄放在一起管」的系統。接下來我們一步一步看，正確的流程到底怎麼做。

第一步：先做 Demo（10 分鐘）

任何專案的第一步，不是「開始做」，而是「先看個樣子」。

比喻：先看樣品屋，再討論格局

你要買房子，不會直接在設計圖上簽約。你會先去看樣品屋，走進去感受空間大小、看看動線、摸摸建材。看完之後你才有「感覺」：客廳太小、廚房要開放式、浴室要乾濕分離。

Demo 就是你的樣品屋。它不需要完美，甚至不需要能用。它只需要讓你「看到」一個大概的樣子，這樣你才能開始說出具體的意見。

怎麼跟 AI 要一個 Demo：

你：「我想做一個客戶管理系統。先不要做完整版，
幫我做一個最簡單的 Demo：

- 一個頁面就好
- 有一個客戶列表（假資料）
- 可以點進去看客戶詳情
- 用最簡單的方式做，不用資料庫，假資料直接寫在頁面裡就好

目的是讓我看到畫面，確認方向對不對。」

10 分鐘後，你就有一個可以看、可以點的東西。這時候你才能真正開始思考：「這個跟我想的一不一樣？」

Demo 的關鍵
Demo 不是最終版本。它就是一個用來「確認方向」的拋棄式原型。不要在 Demo 上修修補補變成正式版，那條路是災難。看完 Demo、確認方向後，才開始正式做。
做 Demo 之前，先找找有沒有現成的
預約、報價單、問卷、會員這類常見的東西，GitHub 上常常已經有人做過、公開放著。動手前先請 Claude 幫你上 GitHub 找一輪，看看別人怎麼做，比從零開始快，別人踩過的坑你也不用再踩。怎麼找、怎麼挑，在第十一章 技術棧。

第二步：看著 Demo 確認邊界

有了 Demo，你現在可以做第三章講的「邊界」了。因為你有東西可以指著說：

  • 「這個列表要加搜尋功能」
  • 「客戶詳情頁不需要編輯功能，只看就好」
  • 「不要做刪除客戶，怕誤刪」
  • 「列表要能按日期排序」
  • 「手機上也要能看，RWD 是必須的」（RWD 是 Responsive Web Design，同一個網頁在電腦和手機上都會自己調整排版）

這些需求在看到 Demo 之前，你可能根本想不到。因為人類是視覺動物：看到東西才能反應。

比喻：看了樣品屋之後的對話

看樣品屋之前：「我想要一個舒服的家。」（模糊到不行）

看樣品屋之後：「客廳太小要加大、廚房要做開放式、主臥的窗戶方向不對，冬天會西曬、浴室要有浴缸不要淋浴間。」

看了之後你才知道自己要什麼、不要什麼。

把你看完 Demo 的所有想法整理成一份清單，分成「要加的」和「不要的」。這份清單就是你的邊界文件。

還沒想清楚？叫它問你

有時候看完 Demo，你只知道「怪怪的」，說不出要什麼。這時不用硬想，反過來讓 Claude 問你。Claude Code 的官方建議也是這樣做：叫它一題一題問，問到可以寫成規格為止，再寫進一個檔案。

你：「我想做一個預約系統，還沒想清楚。
先問我問題，一次問幾個，
問到你可以寫成規格為止，再寫進 SPEC.md。」

它會一組一組問：一個時段可以幾個人預約？客人取消要不要通知你？要不要收訂金？哪些這次先不做？你回答完，邊界清單就在 SPEC.md 裡了。之後開新對話照這份做，對話乾淨，完成的標準也寫在紙上。

第三步：規劃架構（最重要的一步）

確認了要做什麼、不做什麼之後，接下來不是直接開始寫程式，而是先把架構規劃好。

比喻：蓋房子的地基

地基是房子最先做、也最不起眼的部分。但地基歪了，上面蓋得再漂亮都沒用，整棟樓都是歪的。

軟體的「地基」就是資料庫設計和架構決策。這些東西一旦確定了，後面要改的成本非常高。

先切到規劃模式

以前的做法，是在每句指令前面加「先不要寫程式」，然後祈禱它真的聽話。現在 Claude Code 有一個規劃模式（plan mode）：它會讀檔案、查資料、寫出一份計畫，但在你核准之前，不會改任何檔案。這一步交給它，比靠一句話擋住可靠。

  • 終端機（打字下指令的那個視窗）：按 Shift+Tab 切換模式，一直按到底下顯示 ⏸ plan mode on。再按 Shift+Tab 就離開。
  • 只想規劃這一句：在指令開頭打 /plan。
  • 桌面版：在 Code 分頁，輸入框下方那一排有模式選單，選 Plan。

計畫寫好後，它會停下來問你怎麼繼續。大致是三種：

  • 核准，讓它開始做。它會照計畫改下去，大部分步驟不再停下來問你。
  • 核准，但每一處修改都先問你。剛開始用、或這次改的是重要的東西，選這個。
  • 不核准，繼續規劃。告訴它哪裡要改，它改完計畫再給你看。

在這一步，你需要跟 AI 討論（不是直接叫它寫程式）的事情有下面四件。它們各自在後面有一整章，這裡先知道要問什麼。

3-1. 資料庫欄位設計

資料庫就像你的檔案櫃。每一格抽屜放什麼、怎麼分類，一開始就要決定好。後面要改抽屜的格局，等於把所有文件搬出來重新分類。

你：「先不要寫程式。幫我規劃客戶資料表的欄位：

必要欄位：姓名、電話、Email、公司名稱
可選欄位：備註、標籤
系統欄位：建立時間、最後更新時間

問題：
1. 一個客戶可以有多個聯絡人嗎？（如果可以，要拆成兩個表）
2. 標籤是固定選項還是自由輸入？
3. 需要記錄誰建立的嗎？（多人使用的話需要）」

表要怎麼拆、欄位怎麼取名、哪些欄位一旦有資料就很難改，在第十五章 資料表與欄位。

3-2. 計算邏輯放哪裡

如果你的系統有計算功能（例如：訂單總金額、庫存數量），你需要決定計算邏輯放在前端（使用者的瀏覽器）還是後端（伺服器，客人碰不到的那一邊）。

放前端 放後端
速度快、體驗好 資料準確、安全
但使用者可以「竄改」 但每次都要等網路
適合：顯示用途（即時預覽價格） 適合：金流相關（實際扣款金額）

先記一句：跟錢和權限有關的，最後都要後端說了算。前端、後端是什麼，下一章 基本知識會講；什麼可以在前面用 JS 算、什麼一定要放後面，在第十六章 前後端邊界。

3-3. 耦合預告：哪些東西會互相影響

耦合的意思是「A 和 B 綁在一起，動了 A 就會影響 B」。在規劃階段，你需要先知道哪些功能是「綁在一起」的，這樣做的時候才不會一改就壞。

比喻：衣櫃跟電線

你在房間靠牆放了一個大衣櫃，結果衣櫃後面剛好是電線的接線盒。現在要修電線，得先把 50 公斤的衣櫃搬開。

如果一開始就知道接線盒在這裡，衣櫃就不會放這個位置。

耦合預告就是先標出「接線盒在哪」，避免以後搬衣櫃的痛苦。

常見的耦合範例：

  • 使用者權限 ↔ 頁面顯示（改了權限規則，每個頁面都要跟著改）
  • 商品價格 ↔ 訂單計算（價格欄位改了，訂單那邊也要改）
  • 上傳功能 ↔ 儲存空間（檔案格式改了，儲存的邏輯也要改）

3-4. SSOT：單一真理來源在哪裡

SSOT（Single Source of Truth，單一資料來源）翻譯成白話就是：同一筆資料只存在一個地方。

比喻：公司通訊錄

公司有一份通訊錄。如果每個部門都各自維護一份，A 部門改了電話，B 部門不知道，就會打到舊號碼。

正確做法：只有一份「正式通訊錄」放在公司系統上，所有部門都看這一份。誰改了，大家都看得到。

那份「正式通訊錄」就是 SSOT。在軟體裡，某筆資料應該只存在一個地方（通常是資料庫），其他地方需要用就去那裡查，不要各自存一份。

在規劃架構時問 AI：

你：「這個系統的 SSOT 在哪裡？
客戶資料的唯一來源是 Supabase 的 customers 表？
還是有些資料會另外存在瀏覽器裡（localStorage）？
我想確認不會出現資料不同步的問題。」

耦合和 SSOT 是專案長大以後最常出事的兩個地方，第十七章 會出事的地方會一個一個拆。

看計畫的時候看什麼

計畫出來了，不用看程式碼，看它打算動到哪幾塊：

  • 會不會新增資料表或欄位？（第十五章 資料表與欄位）
  • 什麼放在頁面上算、什麼放在後面算？跟錢和權限有關的放哪裡？（第十六章 前後端邊界）
  • 同一筆資料會不會存成兩份？這次改動會不會牽動別的功能？（第十七章 會出事的地方）
  • 它說要「順便」改的那些，是不是你這次要的？

這幾個問題現在看不懂沒關係，第十三到第十七章就是在教你看這些。現在先養成習慣：它動手之前，你先看到它要動哪裡。

第四步：正式開始寫

做完前三步，你現在有了：

  1. 一個看得到的 Demo（知道長什麼樣）
  2. 一份邊界清單（知道要什麼、不要什麼）
  3. 一份你看過、核准過的計畫（知道資料結構、技術選擇、耦合風險）

現在才是正式開始寫程式的時候。而且因為前面的功課做足了，你下指令的品質會好很多：

你：「根據我們剛才討論的架構，開始正式實作。

先做第一個功能：客戶列表頁
- 資料從 Supabase 的 customers 表讀取
- 欄位：姓名、公司、電話、最後聯絡日期
- 預設按最後聯絡日期排序（最近的在上面）
- 頂部有搜尋框，即時過濾（前端過濾）
- RWD，手機版用卡片式而不是表格
- 不要做分頁，先用無限滾動
- 不要做刪除功能

做完這個再做下一個，一次做一個功能。」
一次做一個功能
不要一口氣叫 AI 做完整個系統。一次做一個功能，確認沒問題再做下一個。這樣出問題才知道是哪裡出的，也比較好修。就像蓋房子，一層一層蓋，每層驗收完才蓋下一層。

做歪了：當場停、往回退

它開始動手後，前面一兩分鐘盯一下。方向不對，不用等它做完：

  • 按 Esc：當場停下。它已經做的會留著，你可以直接告訴它往哪裡改。
  • 打 /rewind，或在空的輸入框連按兩次 Esc：倒回前一步。會跳出你送過的每一句話，選要回到哪一句，可以只倒回程式、只倒回對話，或兩個一起倒回。
  • 同一件事糾正兩次還不對，不要糾正第三次。打 /clear 開新對話，把剛剛學到的寫進一句更完整的指令，重來通常比較快。
倒回不等於版本控制
/rewind 只管 Claude 在這段對話裡用它自己的編輯工具改過的檔案。它跑指令改到的其他檔案、你自己在別的地方改的東西，都倒不回來。它是「這一輪的復原鍵」，不是存檔。真正的存檔要用版本控制（Git），做法見附錄 常見問題。

為什麼不能跳過第二步和第三步

警告
如果你跳過第二步（確認邊界）和第三步（規劃架構）直接開始做，你會花更多 Token 來回修改。

因為你省掉的不是「時間」，而是「思考」。那些你沒想清楚的問題，不會消失，它們只會在你做到一半的時候爆出來，而且修起來的成本是事先想清楚的 5 到 10 倍。

改設計圖只要擦掉一條線重畫。改已經蓋好的牆，要拆、要補、要重新粉刷。這就是第三章水電管線的道理。

常見的「跳過就會後悔」的情境：

跳過了什麼 後果 修復成本 一開始本來只要
沒確認要不要多語言 做完才加 i18n（多國語言），30 個檔案全部要改 是一開始就做的 10 倍 說一句「要能切換中英文，文字放語言檔」
沒確認權限設計 做到一半才發現「管理員跟一般使用者看到的頁面不同」，整個路由要重寫 是一開始就規劃的 5 倍 列出有哪幾種人、各看得到什麼
沒設計好資料庫 做到第三個功能才發現表格結構不對，要搬資料（migrate）還可能丟資料 是一開始就設計好的 8 倍 在計畫裡先看一眼它要開哪些表、哪些欄位
沒確認手機版需求 整個畫面做完才說要 RWD，每個元件都要調整 是一開始就考慮 RWD 的 3 倍 說一句「手機也要能看」

「一開始本來只要」那一欄都很短。事前一句話，事後一大包。

本章小結：蓋房子的完整流程

把整個流程用蓋房子來比喻：

Step 1 看樣品屋（Demo）
你走進建商的樣品屋，感受空間大小、看看格局、摸摸建材。這讓你從「我想要一個家」變成「我想要這種感覺的家」。

Step 2 跟建築師討論格局（確認邊界）
你指著樣品屋說：「客廳要再大一點、廚房要開放式、不要浴缸要淋浴間、這個儲藏室不需要。」你說出了「要什麼」和「不要什麼」。

Step 3 看設計圖（規劃架構）
建築師畫出設計圖、結構圖、水電配置圖，你看過、點頭了才動工。你確認地基怎麼打、管線怎麼走、承重牆在哪裡。這些一旦動工就很難改。規劃模式就是「先交設計圖、你簽了才開工」。

Step 4 動工（正式開始寫）
一切確認完畢，才開始打地基、灌漿、砌牆。一層一層蓋，每層驗收。師傅做歪了，當場喊停。

你不會跟建築師說「幫我蓋房子」就等交屋。跟 AI 做專案也一樣。

記住這個流程：Demo → 確認 → 規劃 → 執行。看起來多花了時間，但實際上省下的是來回修改的 Token、砍掉重練的時間，以及抓不到 bug 的挫折感。

給自己的提醒
下次你打開 Claude Code 想說「幫我做一個預約系統」的時候，先停三秒鐘，改成說：

「幫我做一個預約系統的最簡單 Demo，先不用完整功能，讓我看看大概的樣子。」

光是這一句話的改變，就能省你好幾個小時。

這章帶走什麼

  1. 先看樣子。先做一個看完就丟的 Demo，看到東西才說得出要什麼。動手前先找 GitHub 有沒有現成的。
  2. 列邊界清單。分「要加的」和「不要的」。想不清楚，叫它問你，寫進 SPEC.md。
  3. 先看計畫。用規劃模式，它在你核准前不會改檔案。看它要動到哪幾塊：資料表、前後端、會不會牽動別的功能。
  4. 一次做一塊，做完就驗收。做歪了按 Esc 停，/rewind 倒回；真正的存檔靠版本控制。
  5. 省掉的是思考，不是時間。事前一句話的事，事後要打牆。

順序有了，接下來要能看懂計畫裡那些字：路徑、前端、後端、網域、路由。下一章 基本知識把它們一次補齊。

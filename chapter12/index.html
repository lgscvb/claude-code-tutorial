第十二章

API：兩邊怎麼講話

上一章選好了材料：頁面放 Cloudflare，資料放 Supabase 或 D1，小程式用 Workers。材料分在不同地方，要彼此講話，靠的就是 API，就像房子要接水接電。你不需要會寫，但要知道它在幹嘛。這章最後要你帶走一句話：每一個 API 都是一扇門，門要守。

API 是什麼？

想像你走進一間餐廳。

你（前端）坐下來看菜單，選好要吃什麼。
服務生（API）把你的點單送進廚房（後端）。
廚房做好菜之後，服務生再端出來給你。

你不需要知道廚房怎麼煮，也進不去廚房。
你只需要知道：菜單上有什麼、怎麼點、點了之後會拿到什麼。

API 的全名是 Application Programming Interface，翻成中文就是「程式之間的溝通介面」。前端、後端是什麼，第五章 基本知識用餐廳的用餐區和廚房講過，這裡接著講兩邊怎麼講話。

簡單說：

  • 前端（你看到的網頁）想要資料 → 跟 API 說「我要 XXX」
  • API 把請求送到後端 → 後端處理完 → 再透過 API 回傳結果
  • 前端收到結果 → 顯示在畫面上

不只頁面跟後端，你的程式去叫外部服務（寄信、收款、查 LINE 訊息），走的也是對方開出來的 API。

為什麼要知道這個？
你跟 Claude Code 說「幫我做一個客戶管理系統」，它會幫你建 API。你看到 GET /api/customers 這種東西時，就知道這是「去拿客戶列表」的意思，而不是一臉問號。

API 的角色定位

沒有人守門的世界
頁面拿著能開所有東西的鑰匙
直接進資料庫，沒有任何規則
→ 誰打開網頁都能讀、能改
→ 每個頁面自己寫查詢
→ 改一個欄位，好幾個頁面都要改
→ 手機 App 跟網頁各寫一套
有 API 把關的世界
頁面只跟 API 講話
→ API 統一檢查身分和權限
→ 規則集中在一個地方
→ 改一次，全部生效
→ 手機、網頁、別的系統都用同一組 API

這裡要分清楚：出問題的是「沒有規則」，不是「頁面直接連資料庫」這個動作本身。第十一章推薦的 Supabase 就是設計成讓頁面直接連：它替授權過的資料表開好 API，再靠 RLS（逐列權限）規定每個人只能讀寫自己的那幾筆。第十三章 架構拓樸會把這種接法畫出來。規則沒開，才是漏洞。

每一個 API 都是一扇門

換個角度看餐廳：服務生每多接一種單，廚房就得多開一個窗口給他進出。後端開出去的每一個 API，都是一扇對外的門。前端從這扇門進來，有心人也從這扇門進來：他不用你的頁面，直接對門送東西。

每一扇門都要問三件事
是誰？沒登入的，擋下來。
能不能？登入了，但這筆不是他的，擋下來。
送來的東西對不對？金額自己重算，欄位自己再檢查一次。

門的來源有兩種。用 Supabase，每張表要你（或 Claude）明確授權（grant）才會開一扇門，開門的同時就要開 RLS；開了 RLS 但還沒寫規則，拿著頁面那把公開金鑰的人什麼都拿不到。用 Cloudflare D1，門是小函式一扇一扇開出來的，每一扇都要自己檢查。

Claude 加功能時，常會順手多開一扇門：一個匯出用的、一個給後台用的。門越開越多，就越可能有一扇忘了上鎖。所以改完要問：這次有沒有新開門？每一扇有沒有檢查是誰？什麼判斷一定要放在門後面（後端）、什麼可以放在頁面上，第十六章 前後端邊界用八個例子細講。

HTTP 方法（點菜的方式）

既然 API 是服務生，你跟服務生講話時，有幾種不同的「動作」。這些動作在技術上叫做 HTTP Methods（HTTP 方法）。敲門的時候，要先講你要做哪一種事。

方法 白話 餐廳比喻 實際例子
GET 「我要看」 看菜單、查目前的訂單 打開商品頁面、查訂單紀錄
POST 「我要新增」 下一筆新訂單 註冊帳號、送出表單、新增一筆資料
PUT 「我要整個換掉」 整張訂單重寫 更新個人資料（全部欄位都重新送）
PATCH 「我要改一部分」 只換訂單裡的一道菜 只改電話、只改暱稱
DELETE 「我要刪掉」 取消訂單 刪除帳號、移除商品
PUT 和 PATCH 差在哪？
PUT 像是把整張考卷擦掉重寫。就算你只改一題，也要把所有答案都重交一遍，漏寫的那幾題可能就變空白。
PATCH 像是用立可白只修一題，其他題目維持原樣。

只改一兩格的情況很常見，所以你會常看到 PATCH。

狀態碼（服務生的回覆）

你跟 API 說「我要 XXX」之後，API 會回一個三位數的代碼告訴你結果。這就是 HTTP 狀態碼。

不用背，但看到的時候要知道什麼意思：

成功的回覆（2 開頭）

代碼 白話 餐廳比喻
200 成功，資料來了 「好的，菜來了」
201 建立成功 「訂單已成立，等候出餐」
204 成功，沒有東西要回 「辦好了」（常見於修改、刪除）

敲門那一邊的問題（4 開頭）

代碼 白話 餐廳比喻
400 你的要求有問題 「菜單上沒這道菜」「你這張單看不懂」
401 不知道你是誰（沒登入） 「請先出示會員卡」
403 知道你是誰，但你沒有權限 「你有卡，但這間包廂不是你訂的」
404 找不到 「那道菜已經下架了」

後端自己的問題（5 開頭）

代碼 白話 餐廳比喻
500 後端出錯了 「廚房出狀況了，我們也沒辦法」
記住這個規則
4 開頭＝敲門那一邊的問題（請求格式錯、沒登入、沒權限）。先看送了什麼、是誰送的。
5 開頭＝後端自己的問題（程式出錯、資料庫連不上）。把錯誤訊息整段貼給 Claude，請它查後端。

有些後端對沒權限的人也回 404，故意不讓他知道這筆資料存在。這也是守門的一種。

動手玩：同一扇門，三個人來敲

A 設計工作室用你做的客戶管理工具。現在有三個人敲同一扇門，要看 A 設計工作室的客戶 123 號。選一個人，看守門和沒守門的後端各回什麼。

全部是假資料，不會送出任何請求。
敲的是這扇門
GET /api/customers/123

誰來敲：

沒守門的後端

還沒有人來敲。

有守門的後端

還沒有人來敲。

這個示範要開 JavaScript 才能按。下面是同一件事的表格版：

誰來敲沒守門的後端有守門的後端
沒登入的人200，資料給出去401，請先登入
別家公司的登入者200，資料給出去403，這筆不是你們的
A 設計工作室的業務200，正常200，正常

自己人來敲，兩個後端回的一樣。差別只在外人來敲的時候，所以平常用起來完全看不出哪個有守門。這就是為什麼要主動問，不能等出事。

用 Supabase 的話，被存取規則擋掉的那幾筆通常不會報錯，而是像沒有這筆一樣查不到。反過來，整張表還沒授權的話，會直接收到「permission denied for table」（代碼 42501）：不是資料不見，是門還沒開。

實際案例：一個「客戶管理」的完整流程

假設你請 Claude Code 幫你做一個客戶管理系統，它多半會建出下面這幾扇門。我們來走一遍完整流程：

1. 新增客戶（POST）

使用者在頁面上填好表單（名稱、電話、Email），按下「送出」。

POST /api/customers

送出的資料（Request Body）：
{
  "name": "B 咖啡店",
  "phone": "04-0000-0000",
  "email": "hello@b-cafe.example"
}

後端收到 → 存進資料庫 → 回傳：

狀態碼：201 Created

回傳的資料（Response）：
{
  "id": 123,
  "name": "B 咖啡店",
  "phone": "04-0000-0000",
  "email": "hello@b-cafe.example",
  "created_at": "2026-11-13T10:30:00Z"
}

前端收到 201 → 顯示「新增成功！」

注意送出去的資料裡沒有「這筆屬於哪家公司」。那一格要後端從登入身分自己填，不能讓前端說了算：前端送什麼都可能被改過，這就是門口要問的「送來的東西對不對」。

2. 列出所有客戶（GET）

GET /api/customers

狀態碼：200 OK

回傳：
[
  { "id": 123, "name": "B 咖啡店", "phone": "04-0000-0000" },
  { "id": 124, "name": "C 花店", "phone": "04-0000-0001" },
  { "id": 125, "name": "D 文具行", "phone": "04-0000-0002" }
]

前端收到資料 → 排成表格顯示在頁面上。

3. 查看單一客戶（GET＋編號）

GET /api/customers/123

狀態碼：200 OK

回傳：B 咖啡店的完整資料

4. 修改客戶資料（PATCH）

B 咖啡店換了電話號碼，只要改這個欄位：

PATCH /api/customers/123

送出的資料：
{
  "phone": "04-0000-0099"
}

狀態碼：200 OK
→ 只有電話被改掉，其他欄位不動

5. 刪除客戶（DELETE）

DELETE /api/customers/123

狀態碼：200 OK 或 204 No Content
→ B 咖啡店的資料被刪除了

修改和刪除成功時，有的後端回 200 加上結果，有的回 204 什麼都不附。兩個都是「辦好了」。

整理一下
看出規律了嗎？同一個路徑 /api/customers，搭配不同的 HTTP 方法，就能做不同的事：
  • GET /api/customers → 看全部
  • GET /api/customers/123 → 看一個
  • POST /api/customers → 新增
  • PATCH /api/customers/123 → 改一個
  • DELETE /api/customers/123 → 刪一個
這就是 API 設計的核心概念。五行，就是五扇門，每一扇都要問：是誰、能不能、送來的對不對。

API 組合排列的概念（RESTful）

上面那種「用 HTTP 方法＋路徑」來操作資料的設計方式，有一個正式的名字叫做 RESTful API。

RESTful 命名慣例

路徑有一些約定俗成的寫法。這是慣例，不是法律，各家寫法不完全一樣；但看懂了，Claude 給你的清單就讀得懂：

慣例 常見的寫法 比較少見的寫法
用名詞，動作交給方法 /api/customers /api/getCustomers
用複數 /api/orders /api/order
一層一層表示關係 /api/customers/123/orders /api/getOrdersByCustomer?id=123
版本號放在路徑裡 /api/v1/customers /api/customers?version=1

路徑（Endpoint）怎麼看

一個 API 的地址叫 Endpoint。看到一串路徑，可以像看地址一樣拆解：

/api/v1/customers/123/orders

拆解：
├── /api        → 表示這是 API（不是一般網頁）
├── /v1         → 版本 1
├── /customers  → 資料類型：客戶
├── /123        → 特定客戶（編號 123）
└── /orders     → 這位客戶的訂單

白話翻譯：「API 第 1 版，去找編號 123 的客戶，然後拿他的訂單」

再多幾個例子：

GET /api/v1/products → 拿所有商品列表
POST /api/v1/products → 新增一個商品
GET /api/v1/products/456/reviews → 看商品 456 的所有評價
DELETE /api/v1/customers/123/orders/789 → 刪掉客戶 123 的訂單 789

Supabase 替資料表開的門也長這樣，只是條件寫在問號後面：

GET https://（你的專案）.supabase.co/rest/v1/customers?id=eq.123

拆開：rest/v1 是第 1 版的資料窗口，customers 是那張表，
id=eq.123 是「id 等於 123 的那一筆」

跟 Claude Code 的關係

同一件事，三種講法：

不知道 API 概念
「幫我做一個可以新增客戶
的功能，然後還要能查詢
跟刪除」
知道 API 概念
「幫我建 RESTful API：
POST/GET/PATCH/DELETE
/api/v1/customers
回傳 JSON，需要驗證」
再進一步：連門一起講
「客戶資料要能新增、查詢、
修改、刪除。先列出會開哪幾扇門
（方法加路徑），每一扇寫明誰能用、
沒登入和別家公司的人各回什麼。
我確認了再寫」

第二種講法比第一種精準，Claude Code 產出的結果也會更符合你的期待。第三種更進一步，不用你會寫程式，只要知道門是什麼、門要守。Claude 列出來的清單，你一扇一扇看過，邊界就守住了。知道這些「菜名」，就能點對菜。

這章帶走什麼

  • API＝程式之間溝通的介面（服務生）。頁面跟後端、你的程式跟外部服務，都靠它講話
  • 每一個 API 都是一扇門：每一扇都要問是誰、能不能、送來的對不對。Supabase 的門要授權才開，開了就要有 RLS
  • HTTP 方法＝你要做什麼動作（GET 看、POST 新增、PUT 整個換、PATCH 改一部分、DELETE 刪）
  • 狀態碼＝服務生的回覆（2 開頭成功、4 開頭敲門那一邊的問題、5 開頭後端自己的問題）
  • RESTful＝API 路徑的常見慣例（用名詞、用複數、一層一層表示關係）
  • Endpoint＝API 的地址，像 /api/v1/customers/123/orders
跟 Claude 怎麼說
動手之前
「這個功能先列出會開哪幾扇門（方法加路徑），每一扇寫明誰能用、沒登入和別家公司的人各回什麼。我確認了再寫。」
「這筆資料屬於哪家公司、哪個人，由後端從登入身分自己填，不要讓前端送。」

改完之後
「這次有沒有新開門？每一扇有沒有檢查登入和權限？」
「新表要開放給頁面用的話，列出你下了哪些 grant、RLS 規則是什麼。」

出錯的時候
「這是錯誤訊息，狀態碼是 4 開頭還是 5 開頭？用白話講是哪一邊的問題。」

API 把各個零件接起來了。下一章把它們畫成一張圖：頁面、資料庫、外部服務各在哪裡，哪一條線不能亂動。

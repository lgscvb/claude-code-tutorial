第十四章

功能怎麼切：一塊只做一件事

上一章把系統畫成幾大塊和幾條線。這一章鑽進其中一塊，看裡面的功能怎麼切。報價單系統做出來了，也會動；三個月後你想把九折改成八五折，Claude 卻說要動好幾個檔案。這一章講它為什麼會變成這樣，以及你不用看懂程式，要怎麼把它擋住。

第一章、第十三章提過的耦合（coupling），這一章放到功能這一層看：功能和功能黏在一起的程度。

用積木蓋的城堡，每一塊各自獨立，拔掉一座塔樓，城牆還在；想換一座新的，拔掉舊的插上去就好。用膠水黏的城堡，零件全黏死在一起，想拆一座塔樓，旁邊的城牆、吊橋跟著碎掉。

上一章看的是系統裡大塊和大塊黏住；這一章看的是一塊裡面，功能和功能黏住。道理一樣：黏在一起，改一個會壞三個。

這一章講的是怎麼不黏：一開始要怎麼切，切好之後怎麼看出 AI 又把它黏回去了。黏起來之後完整的出事情境，在第十七章 會出事的地方。第一章說的「知道邊界」，放到功能這一層，就是知道每一塊管到哪裡為止。

這一章要回答的兩件事
不懂這個，讓 AI 一直改下去會怎樣？
每一次「順便加一下」，都加在現成的那一塊裡。半年後，改一條折扣規則要動好幾個地方，漏掉一個數字就對不起來，而且沒有人說得出這個系統到底有幾個功能。

懂了以後，你能說出哪一句話？
「這次改動屬於哪一個功能？只動那一塊。需要動到別的地方，先停下來問我。」

Function 是什麼：店裡的一個工作站

比喻：巷口的早餐店。

早上七點最忙的時候，三個人各站一個位置：

點餐台：聽客人說要什麼，寫成一張單子。
煎台：照單子把餐做出來。
收銀台：照單子算錢、收錢、找零。

煎台的阿姨不需要知道蛋餅賣多少錢，收銀的人不需要會煎蛋。那張單子，是他們之間唯一的溝通方式。

程式裡的 function（中文叫「函式」，這一章直接說「功能」）就是一個工作站。每一個功能有三件事要講清楚：

  • 輸入：進來的東西。收銀台收到的是一張點單。
  • 輸出：交出去的東西。收銀台交出應收金額和找零。
  • 它不該順手做的事：收銀台不改單子上的品項，也不幫忙煎蛋。

上一章和第十一章 技術棧說的「小函式」，指的是放在雲端、有人按鈴才醒來的一小段後端。這一章講的是程式裡面的一個步驟，為了不搞混，一律叫「功能」。

早餐店的工作站，和報價單系統裡的一個功能，畫出來是同一個形狀：

早餐店裡
進來一張點單
工作站收銀台
交出去應收金額、找零
不順手做改單子上的品項、幫忙煎蛋
報價單系統裡
進來（輸入）小計、客戶等級
功能套折扣
交出去（輸出）折扣後金額
不順手做存資料、寄信、改報價單的其他內容

第三件事容易被忽略

煎台的阿姨看到熟客，順手把紅茶換成大杯，沒寫在單子上。心意是好的。

但收銀台照單子收了中杯的錢。月底盤點，大杯的杯子少了一批，沒有人知道為什麼。

程式裡這叫副作用（side effect）：一個功能除了交出該交的東西，還另外動到外面的東西：存資料、寄信、改別人的紀錄。

副作用不一定是壞事。「寄給客人」這個功能，它的工作就是寄信。壞的是名字上沒寫、也沒有人知道的那一種。

你不用會寫 function，但要問得出這三件事。Claude 寫完任何一個功能，都可以叫它用三行回報。答不清楚，或者第三行特別長，就是有東西要再問。

跟 Claude 怎麼說
「這個功能，用三行告訴我：輸入是什麼、輸出是什麼、它另外還動了哪些東西（存資料、寄信、改別的紀錄）」
「這一塊只負責算，不要在裡面存資料或寄信」
「把這個專案的每個功能列成表：名字、輸入、輸出、副作用」

一個功能只做一件事：把報價單切成五塊

換成你的生意。你請 Claude 做了一個報價單系統，按下「送出」之後，其實發生了五件事：

功能 進來 交出去 不該順手做
算金額 品項、單價、數量 小計 套折扣、存檔
套折扣 小計、客戶等級 折扣後金額、折扣說明 存檔、寄信
產生 PDF 整張報價單（金額已算好） 一個 PDF 檔 重算金額。它只印，不算
寄給客人 PDF、收件人 寄成功或失敗 改報價單的內容
記到客戶紀錄 哪位客戶、發生了什麼事 一筆紀錄 碰報價單、碰金額

這個原則有名字，叫單一職責（Single Responsibility）：一塊只做一件事，而且這件事只有它在做。

那誰把五塊串起來？

店長。

人多的時候，店長站在中間喊：「三號單做好了沒？好了交給收銀。」他不煎蛋、不收錢，只管順序。

程式裡也有這一塊，可以叫它「送出報價單」：照順序叫五個功能，把上一塊交出來的東西遞給下一塊。它可以很短，但有一條規矩：它自己不算錢、不排版。規則一旦寫進店長的腦袋，五塊就又纏回去了。

全部塞在一起，改折扣的時候差在哪

這樣會出事：一大塊「處理報價單」
裡面從頭寫到尾：
算小計 → 滿萬打九折 → 排 PDF 版面 → 寄 Email → 寫客戶紀錄

把九折改成八五折：
- 打開這一大塊，在中間找到那一行
- 改完，五件事都要重測，因為寫在一起
- 列表頁、月報表各抄了一份折扣，也要改

動三個地方，檢查全部
這樣才對：切成五塊，加一個店長
算金額｜套折扣｜產生 PDF｜寄給客人｜記到客戶紀錄
「送出報價單」照順序叫它們

把九折改成八五折：
- 改「套折扣」這一塊
- 其他四塊沒有碰，只是收到的數字不一樣
- 列表頁、月報表讀的是報價單上算好的金額，自己不算

動一個地方

兩個版本今天跑出來的結果一模一樣。客人看不出差別，你也看不出差別。差別在三個月後你要改東西的那一天。

這也是它難防的原因：纏起來的時候，畫面上什麼都看不出來。

切開的另一個好處：可以整塊換掉

產生 PDF、寄信這種每一家公司都需要的功能，多半已經有人做好了，放在 GitHub 上，或做成現成的服務。功能有切開，才換得進去：只要它收的東西和交出來的東西對得上，裡面是誰寫的都沒關係。所以動手之前先找現成的。怎麼找、怎麼判斷能不能用，照第十一章 技術棧的「先上 GitHub 找」。

切好的每一塊，還有幾個問題要回答，各有一章在講：整個系統有哪幾個大塊、怎麼連，是上一章第十三章 架構拓樸；「記到客戶紀錄」要寫進哪張表、哪些欄位，看下一章第十五章 資料表與欄位；這一塊該放前端還是後端，看第十六章 前後端邊界。

跟 Claude 怎麼說
「按下『送出報價單』之後，總共做了幾件事？一件一件列出來」
「把這幾件事拆成各自獨立的功能，另外用一個『送出報價單』照順序叫它們。它自己不要有任何計算」
「產生 PDF 和寄信，先上 GitHub 找有沒有現成的，列兩三個給我選，不要自己從頭寫」

AI 是怎麼把功能寫纏的：三種纏法

沒有人一開始就想寫成一大塊。纏，是一次一次「加一下」加出來的。常見的有三種，每一種都有一個不用看程式就看得到的徵兆。

纏法一：「順便加個⋯⋯」

你說：「寄出報價單的時候，順便記到客戶紀錄。」對 Claude 來說，最短的路是打開「寄給客人」那一塊，在最後面多寫幾行。能動，你也滿意。然後你又說了幾次「順便」：

  1. 一開始
    寄 PDF 給客人
  2. 「順便記到客戶紀錄」
    寄 PDF 給客人＋寫一筆紀錄
  3. 「順便把狀態改成已送出」
    寄 PDF 給客人寫一筆紀錄＋改報價單狀態
  4. 「順便用 LINE 通知業務」
    寄 PDF 給客人寫一筆紀錄改報價單狀態＋通知業務
  5. 「寄之前順便重算一次，確保金額是最新的」
    寄 PDF 給客人寫一筆紀錄改報價單狀態通知業務＋重算金額

名字還叫「寄給客人」，裡面已經是五件事。

有一天客人說信沒收到，你按了「重寄」。客戶紀錄多了一筆，業務的 LINE 又響一次，金額被重算了。中間你剛好調過價，客人這次收到的數字和上次不一樣。你只是想重寄一封信。

徵兆按鈕的名字，和它實際做的事對不上。你想只做其中一件，做不到。

纏法二：同一段計算，抄了三份

你說：「列表頁也要顯示折扣後的金額。」Claude 每次開工不會把整個專案讀完，只讀它判斷跟這次有關的檔案。這次它讀了列表頁附近的東西，沒看到別的地方已經算過折扣，就在列表頁再寫一次。做月報表的時候，又一次。

三份今天算出來一樣。等你改了其中一份，另外兩份還是舊的。

徵兆改一個地方，三個頁面的數字不一樣。或者同一個毛病修好了，過幾天在別的頁面又出現一次。

上一章的「資料的家」講的是同一筆資料只存一份。這裡是同一個道理用在規則上：同一條規則只寫一份，其他地方都來問它。

纏法三：偷偷去改別人的資料

你說：「PDF 產生之後，報價單要顯示已送出。」Claude 就在「產生 PDF」裡，直接把報價單的狀態改掉。從此你只是想預覽一下 PDF，報價單就變成「已送出」。

這就是煎台阿姨順手換的那杯大杯紅茶。事情做了，但做的人不該是它，也沒有人知道是它做的。

徵兆你沒動的資料自己變了。只是打開來看一下、預覽一下、匯出一下，某個狀態或日期就跟著變。

三種纏法，同一個原因

Claude 每次只解決你眼前講的那一句，而且挑最近的地方下手。它沒有做錯事，是沒有人告訴它這一塊管到哪裡為止。所以同一個需求，換一種講法，結果就不一樣：

這樣會出事
你：「寄出的時候順便記到客戶紀錄」

Claude：在「寄給客人」最後面加了幾行

「寄給客人」從此做兩件事。
重寄一次，紀錄就多一筆
這樣才對
你：「寄出之後要記到客戶紀錄。這是另一個功能，不要寫在『寄給客人』裡面。放到『送出報價單』的流程，排在寄信後面」

Claude：新開一塊，流程多一步

「寄給客人」沒有變。
重寄只會寄信
跟 Claude 怎麼說
「這是一件新的事，不要加在現有的功能裡。另外開一塊，再告訴我要從哪裡叫它」
「動手前先找一下，專案裡是不是已經有算折扣的地方。有的話用那一個，不要再寫一份」
「這個功能除了它該交出來的東西，還改了哪些資料？全部列出來」

切得好不好：四個不用看程式的檢查

你不需要打開程式碼。下面四件事，用問的就知道。

檢查一：能不能用一句話說完

「套折扣：照客戶等級和小計，算出折扣後的金額。」說得完。

「處理報價單：算金額，然後套折扣，還要產生 PDF，順便寄出去⋯⋯」每出現一次「然後」「還要」「順便」，就多一件事。

例外只有店長那一塊。它的一件事就是「照順序叫人」，所以它的說明裡會有「然後」，但不該出現任何規則。

檢查二：名字是不是「動詞＋受詞」

功能的名字通常是英文。你不用背，叫 Claude 把每個名字翻成中文念給你聽就好。

名字 念成中文 聽起來
calculateSubtotal 算小計 一件事，知道交出什麼
applyDiscount 套折扣 一件事
sendQuoteEmail 寄報價單的信 一件事
handleQuote 處理報價單 處理什麼？裡面多半不只一件
processData 處理資料 哪些資料、處理成什麼，都沒說
quoteManager、utils 報價單管理、工具 雜物抽屜，什麼都往裡面放

念出來是「處理某某」「管理某某」的，不一定有問題，但值得多問一句：「這裡面到底做了幾件事？」

檢查三：改它的時候，Claude 說要動幾個檔案

改一條既有的規則，理想是動一個地方。Claude 說要動四、五個檔案的時候，先別讓它動，問它：「為什麼一條規則住在這麼多地方？」

這個檢查只適用「改既有的規則」。新增一整個功能，本來就會動到好幾個檔案，那是正常的。

檢查四：同一條規則，是不是只出現一次

請 Claude 在整個專案裡找「九折」這條規則出現在幾個地方。答案是一，沒事。答案是三，你就找到了纏法二。

切太細也不對

「一塊只做一件事」不是越碎越好。把套折扣再切成「判斷有沒有滿萬」「乘以零點九」「四捨五入」三塊，想搞懂一個折扣要翻三個地方，一樣難維護。

要不要分開，問這一句
「這兩件事，會不會因為不同的理由被改？」

折扣怎麼算，是你跟業務決定的。PDF 長什麼樣，是看美觀。信怎麼寄，是看客人習慣用 Email 還是 LINE。三個理由、三個時間點，所以分三塊。

反過來，「打九折」和「折完四捨五入」總是一起改，放在同一塊就好。

還是會有分不乾淨的。報價單上那一句「VIP 已折 200 元」的說明文字，該由「套折扣」產生，還是由「產生 PDF」自己寫？兩邊都說得通。遇到這種情況，選一邊、寫下來，比爭論哪一邊才正確重要。寫在哪裡，下面「功能清單當合約」那一節會講。

跟 Claude 怎麼說
「把每個功能用一句中文說明它做什麼。說不完，或要用到『然後』的，標出來」
「如果我要把九折改成八五折，你需要動哪些檔案？先列給我看，不要動手」
「折扣的計算規則，在整個專案裡出現在幾個地方？列出檔案和位置」

對 AI 開規格：四行講完

前一節是事後檢查。更省事的做法，是一開始就講清楚。要加一個功能的時候，給 Claude 四行：

  1. 輸入什麼
  2. 得到什麼
  3. 遇到怪情況怎麼辦
  4. 不准動哪裡

前兩行就是開頭講的「進來」和「交出去」。後兩行多數人不會講，也正好是 AI 常常自己決定的地方。

怪情況：你不講，它就自己挑一個

早餐店的怪情況是「蛋餅不要蛋」。報價單的怪情況長這樣：滿萬打九折，VIP 再折 200 元，兩個優惠可以一起用。一張小計 12,000 元的 VIP 報價單，應付多少？

先打折、再減 200：12,000 × 0.9 − 200 = 10,600 元
先減 200、再打折：（12,000 − 200）× 0.9 = 10,620 元

差 20 元。兩種算法都說得通，Claude 會挑一種，而且不一定告訴你。這不是程式問題，是你的生意規則，只有你能決定。

其他常見的怪情況：數量填 0 或負數；小計剛好 10,000 元算不算「滿萬」；折完有小數怎麼進位；客人沒留 Email。

你不需要自己想到全部。Claude 很會列怪情況，你負責選。

不准動哪裡：這一行就是邊界

開頭說的「不該順手做的事」，寫成規格就是這一行。沒有這一行，三種纏法都擋不住。

這樣會出事：只講要什麼
「幫我加折扣功能，滿萬打九折，VIP 再折 200。」

加在哪一塊？它決定。
先折還是先減？它決定。
會不會順手存檔？不知道。

功能會動，邊界沒有人定
這樣才對：四行都講
輸入：小計、客戶等級
輸出：折扣後金額、折扣說明
怪情況：先打折再減 200；剛好一萬也算滿萬⋯⋯
不准動：只算，不存檔、不寄信

它知道這一塊管到哪裡為止

完整寫出來是這樣，可以直接照這個格式改成你的：

幫我做「套折扣」這個功能。先不要寫，把你的理解講一次給我確認。

輸入：小計金額、客戶等級（一般或 VIP）。

輸出：折扣後金額，加一句折扣說明（例如「滿萬九折」）。沒有折扣的時候，說明留空。

規則和怪情況：
- 小計滿 10,000 元打九折，剛好 10,000 元也算。
- VIP 再折 200 元。兩個可以一起用，先打折、再減 200。
- 金額四捨五入到整數。折完低於 0 就算 0。
- 小計是 0 或負數，回報錯誤，不要自己猜。

不准動：
- 這一塊只負責算。不可以存資料、不可以寄信、不可以改報價單的其他欄位。
- 別的地方要用到折扣，一律來叫這一塊，不要自己再算一次。

寫完告訴我：動了哪些檔案、有沒有碰到這一塊以外的東西。

看起來很長，但每一行都是你本來就知道的事。折扣怎麼算是你的生意，不是程式。你只是把它從腦子裡搬到紙上。

「我要加一個功能，先不要寫。你問我問題，把輸入、輸出、怪情況、不准動的地方問清楚，整理成四行給我確認」
「這個功能有哪些怪情況？列出來，每一個寫你打算怎麼處理，我來選」
「它只負責算，不可以存資料、不可以寄信。別的地方要用，一律來叫它」

功能清單當合約：牆上那張職責表

早餐店牆上貼的那張表。

新來的工讀生第一天上班，店長不會把整間店從頭教一次。牆上貼著一張表：點餐台做什麼、煎台做什麼、收銀台做什麼、哪些事不歸你管。看完就能站上去。

Claude 每開一個新對話，都是第一天上班的工讀生。上一次講好的邊界，它不記得。所以要有那張表。

在專案裡放一份功能清單。檔名隨你，例如 docs/功能清單.md。每個功能一小段：

## 套折扣
- 進來：小計、客戶等級
- 交出去：折扣後金額、折扣說明
- 不碰：資料庫、寄信、報價單的其他欄位
- 住在這裡的規則：滿萬九折；VIP 再折 200；先打折再減

## 產生 PDF
- 進來：整張報價單（金額已算好）
- 交出去：一個 PDF 檔
- 不碰：金額（只印不算）、報價單狀態
- 住在這裡的規則：版面、字體、頁尾的公司資訊

## 送出報價單（串流程）
- 照順序叫：算金額 → 套折扣 → 產生 PDF → 寄給客人 → 記到客戶紀錄
- 不碰：任何計算、任何版面

（其他功能照同樣格式）

前面那個分不乾淨的問題，折扣說明文字歸誰，答案就寫在這裡。清單上寫「套折扣」交出折扣說明，那就是它的事。

三個時間點會用到它

改之前，問一句：「這次改動屬於清單上的哪一個功能？」它的回答只有三種：

Claude 的回答 代表什麼 你怎麼做
「屬於『套折扣』」 正常 只准動那一塊
「會動到『套折扣』和『產生 PDF』」 有東西跨過邊界了 先停。問它：為什麼 PDF 需要知道折扣怎麼算？
「清單上沒有」 這是一個新功能 新開一塊、清單加一段，不要塞進舊的

改完之後，請它更新清單，順便問：「有沒有哪一塊做的事變多了？」

偶爾巡一次，請它拿清單對照實際的程式：「有沒有清單上沒寫，但程式裡做了的事？」這一句抓的是纏法三。

為什麼說它是合約

合約不是每天拿出來讀的，是出事的時候有東西可以對。清單上寫了「產生 PDF 不碰金額」，哪天 PDF 上的金額不對，只有兩種可能：問題不在 PDF 那一塊，或者它違約了。兩種都比「不知道從哪裡查起」好。

清單會過期
Claude 讀到清單，不代表每次都照做；改完也不一定記得更新。所以「改之前先讀清單、改完更新清單」要寫進專案的 CLAUDE.md（第十章 Claude Code 怎麼用講過），你自己偶爾也要問一次上面那句巡查的話。

清單和程式對不上的那一天，它就只是一張沒人看的表。
跟 Claude 怎麼說
「讀完整個專案，整理一份功能清單：每個功能叫什麼、進來什麼、交出什麼、不碰什麼、哪些規則住在這裡。存成 docs/功能清單.md」
「在 CLAUDE.md 加上：改任何功能之前先讀 docs/功能清單.md，說明這次改動屬於哪一個功能；改完更新清單」

要改 要檢查：沒有要改，但和被改的東西寫在同一塊 不受影響

這個示範要開 JavaScript 才能按。下面是同一件事的文字版：三種改動，兩種寫法各要動幾塊。

改動 纏在一起 切開
改折扣規則（九折改八五折） 要改 3 處（三份折扣都要改），連帶檢查 6 件 要改 1 處（套折扣），連帶檢查 0 件
改 PDF 版面（多一欄備註） 要改 1 處，連帶檢查 4 件（同一大塊裡的其他四件事） 要改 1 處（產生 PDF），連帶檢查 0 件
改用 LINE 通知 要改 1 處，連帶檢查 4 件 要改 1 處（寄給客人），連帶檢查 0 件

三種改動，切開的版本每次都是改一塊。纏在一起的版本不是每次都要改很多地方，改 PDF 版面也只改一處，但每次都得把同一塊裡的其他事重新確認一遍。

所以纏的代價有兩種：要改的地方變多，以及每次改完都不敢確定沒碰壞別的。第二種更磨人，因為它每一次都發生。

切開的版本那個 0，不是說改完不用測，整個流程還是要從頭跑一次看結果。它的意思是：別塊的程式沒有被打開過，你不用擔心它被碰到。

真實的專案不會像切開的版本那麼整齊，總有一兩塊黏著，這沒關係。你要的不是零，是每次改之前數得出來，而且這個數字沒有一個月比一個月大。

「這次改完，把同一塊裡的其他功能都跑一次，確認沒被碰壞，結果列給我看」
「列表頁和報表不要自己算折扣，改成讀報價單上已經算好的金額」

本章術語表

這些詞會出現在 Claude 的回覆裡。看得懂就好，不用背。

術語 白話 早餐店裡是什麼
Function（函式） 一個有名字的工作步驟：收東西、做事、交東西 一個工作站
Parameter（參數） 交給功能的東西，就是輸入 遞進來的點單
Return value（回傳值） 功能做完交出來的東西，就是輸出 算好的金額、做好的餐
Call（呼叫） 一個功能請另一個功能做事 店長喊：「三號單，交給收銀」
Side effect（副作用） 交出結果以外，另外動到外面的東西：存資料、寄信、改紀錄 順手換成大杯
Single Responsibility（單一職責） 一塊只做一件事 煎台只煎，收銀只收
Duplicate code（重複程式碼） 同一條規則被抄到好幾個地方，就是纏法二。反過來的原則叫 DRY（Don't Repeat Yourself，不要重複自己） 三個人各背一份價目表
Coupling（耦合） 功能黏在一起的程度。黏得越緊，改一個越容易壞別的 煎台和收銀台共用一本會被塗改的價目表
Edge case（怪情況） 平常不太遇到、但遲早會遇到的特殊狀況。也有人翻成「邊界情況」，跟這一章說的「邊界」（每一塊管到哪裡）不是同一件事 「蛋餅不要蛋」
Spec（規格） 動手之前寫下來的「要做成什麼樣」 點單本身
Refactor（重構） 做的事不變，只整理裡面的結構。把一大塊切成五塊就是重構 重排工作站的位置，菜單不變

這章帶走什麼

  • 每個功能講清楚三件事：進來什麼、交出什麼、不該順手做什麼。
  • 一塊只做一件事，同一條規則只寫一份。串流程的「店長」只管順序，自己不算錢。
  • AI 的三種纏法：「順便加」、同一段計算抄三份、偷偷改別人的資料。看徵兆就抓得到，不用讀程式。
  • 不是自己寫，是知道每一塊管到哪裡為止。五塊功能都可以交給 Claude 寫，但「有哪幾塊、每一塊進來什麼、交出什麼、不准碰什麼」這張表要你來定，而且在它動手之前講。邊界畫不到百分之百乾淨，選一邊、寫進功能清單，之後照清單走。

下指令：目標、邊界、情境

你給 AI 的每一句話叫 Prompt（提示詞）。學會怎麼寫好 Prompt，就是學會怎麼寫「讓員工一次做對的工作交辦事項」。

上一章講到，AI 是在接龍，你沒講的它只能猜，而且每一輪來回都要重讀整段對話、都要花錢。這章教你怎麼講：一次把要什麼、不要什麼、在什麼狀況下講清楚，讓它一輪就做對。

Prompt 和 Prompt Engineering

先搞清楚兩個詞：

  • Prompt：你給 AI 的「工作交辦事項」。你打的每一句話，每一段指令，都是 Prompt。
  • Prompt Engineering：學會怎麼寫出「讓 AI 一次做對」的交辦事項。不是什麼高深技術，就是「把話說清楚」的學問。
比喻：交辦事項寫得好不好

你請一個新來的助理幫你買咖啡。

你說：「幫我買咖啡。」他可能買了一杯美式、一杯拿鐵、或是三合一即溶。因為你沒講清楚。

你說：「去樓下便利商店買一杯大杯冰美式，不要加糖。」他一次搞定，不用再打電話問你。

Prompt Engineering 就是學會寫出第二種交辦。

三層溝通模型：目標、邊界、情境

每一次跟 AI 溝通，你需要想清楚三層東西：

  1. 目標（要什麼）：你希望 AI 產出什麼結果
  2. 邊界（不要什麼、做到哪裡）：你不希望 AI 做什麼、哪些是禁區、做到哪裡停
  3. 情境（在什麼狀況下）：目前的背景、限制條件、已有的東西

很多人只講了第一層（我要一個購物車功能），其他交給 AI 猜。你收到的東西可能完全不是你要的，但你也不能怪 AI，因為你沒告訴它不要什麼、做到哪裡。

核心觀念
「不要什麼」比「要什麼」更重要。

因為「要什麼」的範圍是有限的，但「AI 可能自作主張做的事」是無限的。你沒說不要，它就可能會做。你得用邊界把它框住。
比喻：裝潢師傅

你跟裝潢師傅說：「幫我裝潢客廳。」

有的師傅很認真，做了天花板造型、電視牆、木地板、間接照明、訂製書櫃。但你只是想刷白漆、換一盞燈。

也有的師傅反過來，只換了燈泡就收工。你其實想連牆一起刷。

師傅做錯了嗎？沒有。兩個都做了「裝潢客廳」這件事。是範圍只有你知道：要做到哪裡、不要動天花板、不要做電視牆、不要換地板，你沒說。

跟 AI 溝通也一樣，兩個方向都會發生：它常常照最小的範圍做；要它順手修東西時，又可能「好心幫你多做」，動到你沒想到的地方。做到哪裡、哪裡不准碰，要你講。

第一個方向，官方的使用建議（Best practices）也講得很直接：Claude 讀需求偏保守，常會做出「剛好滿足字面要求」的最小版本，因為它看不到你心裡期待多少。你要的是完整版，就明講，例如「做完整一點：沒有資料的時候、出錯的時候畫面長怎樣，也一起做」。第二個方向，就是本章一直在講的邊界。

你不知道可能有什麼問題

三層模型的「情境」這一層最容易被忽略，因為你不知道它不知道什麼。

比喻：蓋房子的故事

有個台灣人要在台灣蓋房子，找了三位建築師：一位來自很少地震的地方，一位來自日本，一位是台灣人。

三棟房子都蓋得很漂亮。

結果地震來了。

第一位建築師蓋的房子出了問題：他的經驗裡沒有地震這件事，設計時根本沒想到要耐震。
日本和台灣的建築師蓋的都沒事，因為他們的「情境知識」包含了「這裡會地震」。

重點不是技術差，而是「情境」不同。你跟 AI 講「幫我蓋房子」，它不一定知道你在台灣、台灣會地震、需要耐震結構。你得主動告訴它。

這就是為什麼很多人覺得「AI 好笨」。不是 AI 笨，是你沒給它足夠的情境。它不知道你的產業、你的客戶、你的限制條件。你得像跟一個外國來的新同事交接工作一樣，把所有背景交代清楚。

Claude Code 官方的使用建議，開頭就講這件事：把它從檔案裡看不到的事告訴它。部署流程只在某個人腦子裡、某個檔案絕對不能讀、上線前一定要過的檢查、預算上限，這些它讀遍整個資料夾也不會知道。手上已經有的東西就直接給，不要用描述的：檔案給路徑、畫面給截圖、錯誤給整段原文。

新手 vs 有效的指令

來看幾個實際的對比，你就知道差異有多大：

新手的說法
「幫我做一個網站。」
有效的說法
「用純 HTML、CSS、JS 做一個
單頁式產品介紹頁，不要打包步驟，
改完直接上傳 Cloudflare。
內容包含：Hero 區塊、三個功能特色、
價格方案比較表、聯絡表單。
深色主題。
先不要後端、不要資料庫。」

為什麼指定「純 HTML、CSS、JS、不要打包」，在第十一章 技術棧會講；Hero 是首頁第一眼那一大塊，網頁各部位的名字在第六章 描述力。

新手的說法
「登入功能壞了，幫我修。」
有效的說法
「會員登入頁按『登入』後，
又跳回登入頁。帳密是對的。
昨天正常，今天早上改過 Header
之後才這樣。F12 的 Console
有一行紅字：（整段貼上）。
先找原因講給我聽，先不要改。」

好的說法講的是在哪裡、看到什麼、應該是什麼、最近改過什麼，再加一句「先找原因，先不要改」。Console 是瀏覽器裡顯示錯誤的地方，按 F12 打開（第六章）；紅字怎麼讀，見附錄 常見問題。

紅字看得懂一些的時候，可以再多給一點線索，例如「Console 顯示 401 Unauthorized，登入的 token 有產生，但好像沒存起來，可能跟 CORS 或 response header 有關」。但猜的原因要明講是「可能」，讓它去查證，不要讓它照你的猜測直接改。

新手的說法
「加一個搜尋功能。」
有效的說法
「在商品列表頁加搜尋框，
用頁面上已經有的資料過濾就好，
不用打 API、不要動後端。
搜尋範圍只包含商品名稱，
不搜描述。打字時即時過濾，
不用按送出按鈕。
沒結果時顯示『找不到相關商品』。」

「打 API」就是去後面的伺服器要資料，API 是什麼在第十二章；什麼可以在頁面上做、什麼一定要放後面，在第十六章 前後端邊界。

先講跟後講，差在要不要打牆

除了「說什麼」，「什麼時候說」也很重要。很多需求如果在一開始就提出來，AI 會自然地把它放進架構裡。但如果你等到做完了才補充，AI 就得把原本的東西拆掉重做。

比喻：水電管線

蓋房子的時候，水電管線要在砌牆之前就埋好。如果牆都砌好了，你才說「欸，這裡加一個插座」，那就得打牆、埋管、補牆、重新粉刷。

本來畫在設計圖上的一條線，變成一整輪的工程。

跟 AI 溝通也一樣。在開始動工前就把需求說完整，改的只是設計圖。動工後才補需求，就是打牆重來。

例子：多國語言（i18n）

i18n 是 internationalization 的縮寫（i 和 n 之間有 18 個字母）。白話說就是：讓你的網站支援多種語言，可以切換。

一開始就說
「做一個產品介紹頁，
要支援中文和英文切換，
文字都放在語言檔案裡，
不要寫死在 HTML。」

AI 從第一行程式碼就照這個方式寫。
做完才說
（網站已做完，30 個檔案，
所有文字都寫死在 HTML 裡）

「欸，加一個英文版。」

AI 要翻遍 30 個檔案，
把每一段文字抽出來，
建立語言檔，重寫引用方式。
改一改還可能改壞其他功能。
記住這個原則
在動工前，把你「可能會要的東西」都先列出來。就算不確定要不要做，也先告訴 AI「之後可能會有多語言、可能會有手機版、可能會多一個管理員角色」，讓它預留位置。砌牆前埋管線，是改設計圖；砌完牆才打洞，是打牆、補牆、重新粉刷。

動工前怎麼把需求想完整，先做一個樣品屋（Demo）看著列清單，是下一章 工作流程的主題。

例子：搜尋功能的邊界比你想像的複雜

你跟 AI 說「加一個搜尋功能」，聽起來很簡單，但搜尋其實有很多種：

搜尋類型 白話 例子
精確搜尋 打什麼找什麼，一字不差 搜「冰美式」只找到冰美式
模糊搜尋 打錯字也能找到 搜「冰美試」也找到冰美式
範圍搜尋 在某個區間裡找 價格 1000 到 5000 元
過濾 Filter 用條件篩選 只看紅色、只看 XL
全文搜尋 搜內文，不只標題 搜「退貨」會找到內文提到退貨的文章
即時搜尋 打字的同時就跑出結果 邊打字，底下的商品列表邊變少
注意
如果你只說「加搜尋功能」，AI 可能只做最簡單的精確搜尋。但你的客人期待的是打錯字也找得到，還能篩選。這就是為什麼邊界要講清楚：要哪幾種、搜哪些欄位、做到哪裡停。

下指令的檢查清單

每次下指令前，過一遍這個清單，可以幫你大幅提高品質、減少來回修改：

目標面（要什麼）

  • 我要的最終產出是什麼？（一個頁面？一張報表？一個能填的表單？一段分析？）
  • 它給誰用的？（客人？同事？管理者？我自己？）
  • 成功的標準是什麼？（能登入就好？還是要有忘記密碼流程？）
  • 有沒有參考範例？（「像 B 咖啡店官網那樣的菜單頁」）

邊界面（不要什麼、做到哪裡）

  • 哪些功能不要做？（不要社群登入、不要會員等級）
  • 哪些做法不要用？（不要需要打包的框架、不要加我沒點頭的套件、不要新增付費服務）
  • 複雜度上限在哪？做到哪裡停？（先做最簡單的版本就好）
  • 有什麼已經做好了，不要動的？（資料表結構已定，不能改；登入流程不要碰）

情境面（在什麼狀況下）

  • 目前用什麼技術？（純靜態頁面放 Cloudflare、資料庫用 Supabase、版本放 GitHub，見第十一章 技術棧）
  • 現有的檔案結構長什麼樣？（列出主要資料夾，或叫它自己先看一遍再講給你聽）
  • 有什麼已知的限制？（免費方案、流量限制、手機要能用）
  • 這是全新專案，還是要加進現有系統？
  • 團隊有幾個人？只有你自己？（只有你一個人維護，就不要做成要一整個團隊才顧得了的東西）
不用每次都寫這麼多
小任務不需要寫完整個清單。但大任務（做新功能、開新專案、改架構）一定要盡量涵蓋。養成習慣之後，你會自然知道哪些該講。

還沒想清楚也沒關係，叫它問你：「我想做一個預約系統，還沒想清楚。先問我問題，問到你可以寫成規格為止。」官方的使用建議也推薦這個做法。

CLAUDE.md：你的「邊界文件」

如果你用 Claude Code，有一個非常重要的檔案叫 CLAUDE.md。它是放在專案資料夾最上層的一個純文字檔（也可以放在專案裡的 .claude 資料夾），Claude Code 每次開新對話都會先讀進去。

比喻：新員工的 SOP 手冊

想像你請了一個新員工。他第一天上班，你會給他一本公司 SOP：「我們用什麼工具」、「我們的命名規則」、「客戶的忌諱」、「出包了找誰」。

CLAUDE.md 就是 AI 的那本 SOP 手冊。你把專案的規則、偏好、禁忌、架構說明寫在裡面。這樣你不用每次開新對話都重複講一遍，AI 每次都會先讀這本手冊。

一個 CLAUDE.md 裡通常會寫什麼：

  • 這個專案用什麼技術（純 HTML、CSS、JS，不用打包工具；放 Cloudflare，資料庫用 Supabase）
  • 寫法的規矩（畫面上的文字用繁體中文、不要加新的套件、註解寫中文）
  • 檔案放哪裡（每一頁一個資料夾放 index.html，共用的樣式放 /styles.css）
  • 不能做什麼（不要改資料表結構、不要動登入流程、不要把密碼寫進程式碼）
  • 常見的坑（例如「這個外部服務一分鐘最多呼叫 60 次」這種，它讀程式碼看不出來的事）
# CLAUDE.md 範例

## 專案規範
- 純靜態網站：HTML、CSS、JavaScript，不用打包
- 放在 Cloudflare，資料庫用 Supabase
- 改完先在我電腦上開起來給我看，我說好再上線

## 禁止事項
- 不要動資料表結構
- 不要在程式碼裡寫入任何密碼或 API Key

不會寫就在 Claude Code 裡打 /init，它會看過你的資料夾，幫你產生一份初稿，你再改。官方建議一份不要超過大約 200 行：寫越長，每次都佔桌面，它也越不容易每條都照做。只寫它從檔案裡看不出來的事，和你已經糾正過它兩次的事。

CLAUDE.md 的好處
寫一次，每個對話都有效。

上一章講過 Context Window 的問題：每次開新對話，前一場對話的內容不會帶過來；同一場對話太長、被自動壓縮時，很前面交代的細節也可能不見。但 CLAUDE.md 是存在檔案裡的，你寫進去的東西，它每次開工都會讀。這是對抗「它又忘了」很有效的方法。
交代不是上鎖
官方文件寫明：CLAUDE.md 對它來說是參考，不是強制設定。它通常會照做，但不保證。真的絕對不准碰的事，要用權限規則或 Hook 來擋，那才是鎖。放在哪一層、它自己記的筆記、怎麼上鎖，在第十章 Claude Code 怎麼用。

這章帶走什麼

  1. Prompt 就是你給 AI 的工作交辦事項，Prompt Engineering 就是學會怎麼寫讓 AI 一次做對的交辦。
  2. 三層溝通模型：目標（要什麼）、邊界（不要什麼、做到哪裡）、情境（在什麼狀況下）。大部分人只講了目標，忘了邊界和情境。
  3. 「不要什麼」比「要什麼」更重要。裝潢師傅的故事：它可能只做最小的範圍，也可能好心多做。做到哪裡、哪裡不准碰，只有你知道。
  4. 你不知道它不知道什麼。蓋房子的故事：情境知識（地震、法規、限制）要主動告訴 AI；手上有的檔案、截圖、錯誤訊息直接給。
  5. 先後順序影響巨大。水電管線的故事：先講是改設計圖，後講是打牆。
  6. CLAUDE.md 是你的邊界文件。寫一次，每個對話都有效；但它是交代，不是鎖。

現在你知道怎麼「說話」了。但光會說話還不夠，你還需要知道正確的「做事順序」：先看樣子、先看計畫、再讓它動手。下一章講工作流程。

跟 Claude 怎麼說

可以直接抄
把邊界講在前面：
「這次只改報價單的畫面，不要動資料表，也不要動後端。如果一定要動到別的地方，先停下來告訴我要動哪裡、為什麼。」

還沒想清楚時：
「我想做一個預約系統，還沒想清楚。先問我問題，一次問幾個，問到你可以寫成規格為止，再寫進 SPEC.md。」

想先比較做法：
「先不要動手。給我兩三個做法，各自的好處、壞處，會動到哪些檔案、會不會加資料表或欄位。」

東西壞了：
「先找原因講給我聽，先不要改。」

要完整版時：
「做完整一點：沒有資料的時候、出錯的時候、手機上長怎樣，都一起處理。」

每次都要遵守的規矩：
「把『不要加新的套件，要加先問我』這條加進 CLAUDE.md。」

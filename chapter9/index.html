第九章

資料庫：開一個，接到你的頁面

第七章把 B 咖啡店的預約頁放上網，第八章替它接上自己的網址。現在客人打得開、填得了，可是按下送出，預約去哪了？哪裡都沒去。這一章開一個資料庫，讓每一筆預約真的存下來，老闆隔天打開就看得到。

先看全貌：這章做完會變成什麼樣

前兩章做的是「讓人看得到」。這一章做的是「讓人留得下東西」。做完之後，整條路長這樣：

頁面怎麼來的（第七、八章做好了）
  1. 你的電腦Claude 在這裡改頁面
  2. GitHub留每一版的紀錄
  3. Cloudflare把頁面放上網
  4. 客人的手機打開 B 咖啡店的網址
預約怎麼存下來（這一章要做的）
  1. 客人按送出頁面把資料打包好
  2. Supabase 的門口先看規則：這個動作准不准
  3. 預約表准的話，寫進一列
  4. 老闆登入 Supabase 後台查看

第一排是頁面從你的電腦一路走到客人手上。第二排是客人填的東西反過來走：從客人手上，經過一道門，存進一張表。那道門是這一章的重點，最後一節會專門講。

資料庫是什麼

先想想 B 咖啡店現在怎麼收預約。櫃檯放一本預約簿，客人打電話來，店員翻到那一天，寫下名字、電話、幾點、幾位。

資料庫就是一本放在網路上、有規矩的預約簿。差別在三件事：

  • 它會擋錯：人數欄只收數字，日期欄只收日期。客人把電話填進人數那格，它直接退回，不會先收下來再讓你頭痛。
  • 它會看人：誰可以寫、誰可以看、誰可以改，事先講好。客人只能寫一筆新的，不能翻別人的。
  • 它不怕擠：十個客人同一秒按送出，它一筆一筆排好收，不會兩個人寫在同一行、互相蓋掉。
白話比喻：

試算表像一本攤在櫃檯上的筆記本，誰經過都能翻、能改、能撕。

資料庫像一個有管理員的登記處。你遞單子進去，管理員先看格式對不對、你有沒有資格，對了才幫你歸檔。你看不到抽屜裡別人的單子，也不能自己伸手進去改。

這一章用的資料庫服務叫 Supabase。它底下是一個完整的 PostgreSQL 資料庫（一種很普遍的資料庫），外面再包好登記處需要的東西：一個讓頁面送資料進來的窗口（API，第十二章細講）、一套看人的規則、一個給你看資料的後台。你不用自己架機器，也不用自己寫窗口。

為什麼不能拿 Google 試算表當資料庫用到底

很多人第一個念頭是：「預約丟進 Google 試算表就好，我天天在用，看得懂。」剛開始真的可以。客人少、只有你一個人在看，試算表撐得住。問題出在後面。

情況Google 試算表資料庫
客人把「三位」寫成「3 個人＋1 小孩」 照收。之後要算總人數，算不出來 人數欄設成數字，填不進去，頁面當場請客人改
店員不小心刪掉一整排 刪了。要翻版本紀錄才找得回來，還不一定發現得了 店員帳號根本沒有刪除的權限
頁面要讓客人寫入 通常要把整份試算表開給程式寫，等於整本筆記本交出去 可以只開「新增一筆」這個動作，其他都不開
兩個客人同時預約最後一個位子 兩筆都收，誰先誰後要人去判斷 可以設規則讓後到的那筆被擋下（第十七章講）
要接會員、查自己的預約、改狀態 越接越亂，公式和程式黏在一起 本來就是為這些事設計的

試算表不是不能用。它的位置在「抄本」：每天從資料庫匯出一份，給會計看、給老闆做報表都很好。但真正以它為準、讓頁面直接寫進去，就是把店裡唯一一本預約簿攤在門口。

一份資料只能有一個家
資料庫和試算表同時存預約、兩邊都能改，遲早對不起來：客人在頁面取消了，試算表那份還在；店員在試算表改了時間，頁面上查到的還是舊的。要兩份，就講清楚「以資料庫為準，試算表是抄本，誰都不准改抄本」。這件事在第十三章 架構拓樸 和第十七章 會出事的地方 會再講一次。

動手前：哪些事 Claude 做，哪些事你做

這一章跟前兩章一樣，大部分的事可以交給 Claude。它會開表、寫規則、改頁面、測試。但有幾件事它不該做，也做不了：

事情誰做為什麼
註冊 Supabase 帳號、設密碼你帳號是你的，密碼只有你該知道
在瀏覽器裡按「允許」讓 CLI 登入你等於把一把鑰匙交給 Claude，要你本人點頭
升級付費、綁信用卡你花錢的事一律自己按
開表、寫授權和規則、留 Migration 紀錄Claude它寫得快；你看它列出來的清單
改預約頁、接上資料庫、測試Claude改完你在手機上自己試一次
刪表、清空資料、刪整個專案你確認後才做刪了就沒了，免費版沒有自動備份

下面每一步都分成三格：要做什麼、跟 Claude 怎麼說（可以直接複製）、你自己要動手的地方。後面再附「做完會看到什麼」和「常見卡住的地方」，讓你知道自己有沒有做對。

以下操作的依據
步驟、畫面上的名稱、免費額度都照 Supabase 官方文件寫，查詢日期 2026-11-13。服務的畫面會改，看到的名稱跟這裡不一樣時，以官方畫面為準，或直接問 Claude：「Supabase 現在的畫面，這個功能在哪裡？去官方文件查。」

步驟一：註冊 Supabase，開一個專案

Supabase 的「專案」就是一個獨立的資料庫，加上它的窗口和後台。B 咖啡店的預約開一個專案就夠了。

步驟一

開一個 Supabase 專案

要做什麼

到 supabase.com 註冊帳號，在後台建一個新專案，取一個好認的名字，例如 b-coffee-booking。

跟 Claude 怎麼說

「我要幫 B 咖啡店的預約頁開一個 Supabase 專案。先去官方文件查現在註冊和開專案的流程、免費版的限制，用白話列給我，我自己去按。」

你自己要動手
  • 註冊帳號。官方註冊頁可以用 GitHub 帳號登入，也可以用 email 和密碼。第七章已經有 GitHub 帳號的話，用 GitHub 最省事。
  • 開新專案時，畫面會要你填專案名稱、設一組資料庫密碼、選一個地區。地區選離客人近的（客人在台灣，就選亞洲的）。
  • 資料庫密碼存進你的密碼管理工具。之後不要貼給 Claude 看，它用不到這組密碼也能做事（下一步用另一種登入）。
做完會看到

專案準備好之後，你會進到這個專案的後台。專案有一個自己的網址，長得像 https://一串英文字母.supabase.co，那串字母叫專案代號。後台有一個 Connect 按鈕，點開看得到這個網址和一把金鑰，下一步會用到。

常見卡住的地方
  • 專案一直在準備中：新專案要一點時間建好資料庫，先去做別的事再回來。
  • 開不了第三個專案：免費版同時只能有兩個在用的專案。不用的那個先暫停或刪掉（刪之前看下面的「刪除」提醒），或改用付費方案。
  • 註冊後要你去信箱確認：照畫面指示去收信，確認完再回來登入。

免費版先知道這幾件事

項目免費版這對 B 咖啡店的意思
專案數同時最多 2 個在用的專案預約一個、練習一個，剛好
資料庫大小每個專案 500 MB只存文字的預約，夠用很久
一週沒動靜會被暫停淡季沒人預約，頁面可能突然送不出去（下面細講）
自動備份沒有備份要自己做（步驟七）
付費方案Pro 每月 25 美元起，含每日備份、保留 7 天，不會因為沒動靜被暫停有真的客人在用、停一天就損失生意時再考慮

以上數字與價格以官方頁面為準（supabase.com/pricing，查詢日期 2026-11-13）。方案會改，升級之前自己再看一次。

步驟二：讓 Claude 接上你的專案

接下來開表、寫規則，都可以在 Supabase 後台用滑鼠點出來。但這一套教的做法是讓 Claude 用 Supabase 的 CLI（在終端機裡用打字操作的工具）去做。理由跟第七章用 wrangler、gh 一樣：有官方 CLI 就先用 CLI。Claude 本來就會打指令，每一個動作都留在畫面上，你看得到它做了什麼；而且每次改資料庫結構都會留一份紀錄檔，之後查得到、退得回去。

步驟二

裝好 Supabase CLI，登入一次，連到專案

要做什麼

在預約頁的資料夾裡，讓 Claude 裝好 Supabase CLI、登入你的帳號，再把這個資料夾連到剛剛開的專案。

跟 Claude 怎麼說

「幫我裝 Supabase 的官方 CLI，照官方文件的方式。裝好之後登入，再把這個資料夾連到我剛開的 b-coffee-booking 專案。需要我在瀏覽器按什麼，先告訴我在哪個視窗、要按什麼。」

你自己要動手
  • 登入時，瀏覽器會打開 Supabase 的頁面，請你登入並確認。先看網址是 supabase.com，再按。畫面如果給你一組驗證碼，照指示貼回終端機。
  • 登入這一步要在終端機輸入東西的話，請 Claude 把指令給你，你自己在終端機打。登入後的權杖會存在電腦系統的鑰匙圈裡，不用你另外記。
  • 如果你切在 Manual 模式，它安裝東西前會先問你；預設的 Auto 模式不一定會問。所以開工前先跟它說：「安裝任何東西前先告訴我要裝什麼、從哪裡裝。」它說了，看一眼是不是 Supabase 官方的 CLI，再讓它裝。
做完會看到

Claude 回報登入成功、已經連到 b-coffee-booking。你的資料夾裡多了一個 supabase 資料夾，之後每一次改資料庫結構的紀錄都會放在 supabase/migrations 裡。

常見卡住的地方
  • 登入的網頁沒跳出來：請 Claude 把登入網址印出來，你自己複製到瀏覽器打開。
  • 連錯專案：你有兩個專案時特別容易發生。請 Claude「列出目前連到的專案名稱和代號」，跟後台網址裡那串字母對一下。
  • Claude 跟你要資料庫密碼：多數動作用登入就夠了。它真的需要時，請它說明為什麼、要用在哪一個指令；密碼由你自己在終端機輸入，不要貼進對話。
不想裝 CLI 也可以
Supabase 有官方的 MCP，也可以讓 Claude 開表、查資料；再不行，後台的 SQL Editor 可以讓你把 Claude 寫好的 SQL 貼進去執行。順序照第十章 Claude Code 怎麼用 講的：有官方 CLI 先用 CLI，沒有才裝 MCP。用後台貼 SQL 的缺點是沒有自動留紀錄，要自己記得存一份。

步驟三：開一張「預約」表

資料庫裡裝資料的地方叫表，長得很像試算表的一個分頁：每一列是一筆預約，每一欄是一種資料（名字、電話、日期）。差別在每一欄都要先講好放什麼，講好就不能亂放。

B 咖啡店的預約頁有哪些格子，表就開哪些欄。第七章做的頁面有姓名、電話、日期、時間、人數、備註，那就是這六欄，再加兩個資料庫自己會填的：每筆的編號、收到的時間。

步驟三

讓 Claude 開表，並留下 Migration 紀錄

要做什麼

照預約頁上的格子開一張 reservations（預約）表。用 Migration 的方式開：先寫成一個紀錄檔，再套用到資料庫上。

跟 Claude 怎麼說

「先讀預約頁的表單有哪些欄位。照這些欄位，用 Supabase CLI 開一個 migration，建一張 reservations 表。人數只收 1 到 20 的整數，姓名、電話、日期、時間不能空白。寫好先給我看 SQL，用白話解釋每一欄，我說可以再套用到資料庫。」

你自己要動手
  • 看 Claude 列出來的欄位，跟頁面上的格子一個一個對。少一欄，客人填了也存不進去；多一欄，問它那是做什麼的。
  • 確認之後，回它一句「可以，套用」。
做完會看到

supabase/migrations 裡多一個檔，檔名開頭是日期時間。到 Supabase 後台的 Table Editor，看得到一張空的 reservations 表，欄位跟你剛剛確認的一樣。

常見卡住的地方
  • 後台看不到新表：先確認 Claude 是套用到「遠端的專案」，不是只在你電腦上的練習資料庫。請它說清楚套用到哪裡。
  • Claude 直接在後台改，沒留紀錄檔：請它補一份 migration，讓紀錄跟資料庫現況一致。
  • 欄位名稱是中文：請它用英文小寫加底線（例如 party_size），中文留在說明裡。程式和資料庫都比較不會出事。

Claude 寫出來的 SQL 大概長這樣。你不用會寫，看得懂在說什麼就好：

-- 建一張預約表 create table public.reservations ( id bigint generated by default as identity primary key, -- 每筆的編號，自動給 created_at timestamptz not null default now(), -- 收到的時間，自動填 name text not null, -- 姓名，必填 phone text not null, -- 電話，必填 reserve_date date not null, -- 預約日期 reserve_time time not null, -- 預約時間 party_size int not null check (party_size between 1 and 20), -- 人數 1 到 20 note text -- 備註，可以空白 );

幾個字看懂就夠：text 是文字，date 是日期，int 是整數，not null 是不能空白，check 是額外的檢查。電話用文字不用數字，因為電話開頭的 0 不能被吃掉。

Migration 是什麼：

裝潢店面時，每次改格局都留一張施工單：哪天、拆了哪面牆、加了哪個插座。半年後要查「這個插座是誰裝的」，翻施工單就知道。

Migration 就是資料庫的施工單。每改一次表的結構，就留一個檔，照時間排好。哪天出問題，看得到是哪一次改壞的；要在另一個專案重建一樣的表，照單施工一次就好。
這章只開到夠用
一張預約表、八個欄位，夠 B 咖啡店起步。之後要加「狀態」（已確認、已取消）、要分店、要會員，表怎麼拆、欄位怎麼定、表跟表怎麼連，留給第十五章 資料表與欄位。現在先記一句：欄位不要讓 Claude 想加就加，每加一欄都要它先講為什麼。

步驟四：開門，再上鎖（授權與 RLS）

表開好了，但現在預約頁還連不進來。這是對的。Supabase 的規矩是：沒交代的，一律不開。要讓頁面寫得進來，要做兩件事。

第一層：授權，決定這張表的門開不開

授權（SQL 裡叫 grant）決定「從頁面來的人，能對這張表做哪幾種動作」。動作有四種：讀、新增、修改、刪除。B 咖啡店的預約頁只需要一種：新增。客人不需要讀別人的預約，更不需要改或刪。

Supabase 在 2026 年改了預設：新建的表不再自動開放給頁面，要明確授權才開。照官方公告，新專案從 2026 年 5 月 30 日起陸續改成這樣，舊專案從 2026 年 10 月 30 日起也一樣。改之前就建好的表，原本開放的動作照舊留著；以前的預設是讀、新增、修改、刪除全開。

所以你的表可能是「什麼都沒開」，也可能是「全部都開」。不用去分是哪一種：請 Claude 先把這張表給頁面的授權全部收回，再明確寫出要開哪幾個動作，最後檢查有沒有多開。這樣新舊專案做完的結果都一樣。後台的 Data API 設定裡有一個 Automatically expose new tables（自動開放新表）的開關，建議關著。

授權沒開的表，頁面連過去會看到「permission denied for table」，代碼 42501。這是門沒開，不是資料不見，請 Claude 只補需要的那幾個動作。

第二層：RLS，決定每一筆准不准

RLS 是 Row Level Security 的縮寫，白話是「逐列的存取規則」。門開了之後，每一個動作還要過一關：這一筆，這個人，准不准？

RLS 有一個很重要的性質：打開之後，沒有寫規則的動作一律擋掉。所以做法是先打開，再一條一條寫「准什麼」，沒寫到的自然都不准。用 SQL 開表時，RLS 不會自動打開，一定要記得開；在後台用滑鼠開表的話，Supabase 會替你打開。

白話比喻：

授權是店門口的告示：「本店只收預約單」。沒寫在告示上的事，店員連聽都不聽。

RLS 是櫃檯店員手上的檢查表：收到一張預約單，看它准不准收。檢查表上只寫了一條「客人可以交新的預約單」，所以客人要求「讓我看今天所有人的預約」，店員照表回答：不行。
步驟四

只開「新增」，打開 RLS，寫一條規則

要做什麼

讓沒登入的客人（Supabase 叫這種身分 anon）只能對 reservations 表做「新增」；打開 RLS；寫一條規則准許新增。讀、改、刪全部不開。

跟 Claude 怎麼說

「再開一個 migration：reservations 表打開 RLS；先收回 anon 和 authenticated 原本的所有授權，再只授權 anon 新增（insert），不要授權讀取、修改、刪除；加一條 RLS 規則，允許 anon 新增預約。寫完列一張表給我看：每個身分能做哪些動作。」

「套用之後，用頁面會用的那把 publishable key 實際試三件事：新增一筆、讀全部、刪一筆。告訴我哪個成功、哪個被擋，被擋的錯誤訊息是什麼。」

你自己要動手
  • 看 Claude 列出來的那張表，確認只有「客人：新增」是打勾的。
  • 看它回報的三個測試結果。新增成功、讀取和刪除被擋，才算過關。
做完會看到

Claude 回報：用頁面的金鑰新增一筆，成功；讀全部，被擋；刪一筆，被擋。後台的 Table Editor 裡多了一筆測試資料（看完可以請它刪掉）。

「被擋」有兩種樣子，都算過關：

  • 回 42501（permission denied）：門根本沒開，最乾淨。
  • 不報錯，但讀全部回一個空清單、刪除刪到 0 筆：門有開，RLS 沒准，所以一筆都碰不到。RLS 擋讀和刪的方式就是這樣，安靜地當作沒有。這時順手請 Claude 到後台確認那筆測試資料還在。
常見卡住的地方
  • 新增時出現「permission denied for table」，代碼 42501：門還沒開，授權少了。（讀全部、刪一筆出現 42501 是對的，那是過關。）不是資料不見。請 Claude 只補「新增」的授權。
  • 新增也被擋，代碼一樣是 42501：門開了，但 RLS 沒有准許新增的規則，或規則寫錯身分。請 Claude 檢查規則是不是寫給 anon。
  • Claude 說「為了方便，先把 RLS 關掉」：不要答應。關掉 RLS 等於檢查表撕掉，任何拿到金鑰的人想讀就讀、想刪就刪。

這一步的 SQL 大概是這樣：

-- 打開 RLS：沒寫規則的動作一律擋掉 alter table public.reservations enable row level security; -- 先收回：舊專案的表可能本來就全開，先全部收回，新舊專案結果才一樣 revoke all on table public.reservations from anon, authenticated; -- 授權：沒登入的客人（anon）只能新增 grant insert on table public.reservations to anon; -- 規則：准許 anon 新增預約 create policy "客人可以新增預約" on public.reservations for insert to anon with check (true);

最後那條規則的 with check (true) 意思是「新的這一筆，不另外檢查，收」。欄位本身的檢查（必填、人數 1 到 20）在開表時已經設好了，還是會擋。想再嚴一點，例如「不能預約今天以前的日期」，可以請 Claude 把條件寫進這裡。

下面這個小示範，把剛剛設好的規則跑一遍。換不同的人、做不同的事，看門口怎麼回答。

先選一個人，再選一個動作。規則就是步驟四設好的那一套。

誰來敲門？

想做什麼？

收下。 有授權新增，RLS 也有准許新增的規則。欄位格式對，就寫進一列。

註：secret key 略過的是 RLS 規則，不是授權。照本章的設定，reservations 只授權給 anon，所以 secret key 也要另外授權給 service_role（secret key 用的身分）才進得去，之後寫後端時記得補。示範裡畫的是補好之後的樣子。外流的危險不會因此變小：補上授權的那一天，它就是萬用鑰匙。

注意前兩個人：來預約的客人和想偷看名單的路人，結果一模一樣。因為他們手上拿的是同一把金鑰，就是寫在頁面裡、誰都看得到的那一把。門口分辨不出誰是好人，只看規則。這就是為什麼把關要靠規則，下一步會再講一次。

步驟五：讓預約頁把資料存進去

資料庫準備好了，最後是讓第七章那個預約頁在客人按送出時，把資料交給 Supabase。第七章說過，這一套不用打包：頁面就是 HTML、CSS、JS，改完直接上傳。所以 Supabase 的程式庫也用不打包的方式載入，在頁面上加一行 <script> 就好。

兩把金鑰：一把可以放頁面，一把絕對不行

Supabase 每個專案有兩種金鑰。分清楚這兩把，是這一章最重要的一件事。

publishable keysecret key
長相開頭是 sb_publishable_開頭是 sb_secret_
可以放哪頁面、手機 App、公開的程式碼，官方說可以公開只能放在後端（伺服器、小函式），官方寫明只在後端用
拿著它能做什麼只能做 RLS 准許的事略過所有 RLS 規則；只要那張表有授權給它，就什麼都能做
比喻店門口的門鈴：誰都能按，開不開門看規則店裡的萬用鑰匙：拿到就能進每一個抽屜

比較早開的專案，後台可能還看得到舊名字：anon key 對應 publishable key，service_role key 對應 secret key。舊的兩把開頭都是 eyJ，長很多。分法一樣：anon 可以放頁面，service_role 不行。官方說舊金鑰預計 2026 年底前淘汰，新專案直接用新的兩把。

secret key 一律不放頁面、不進 GitHub
Supabase 會擋掉從瀏覽器送來的 secret key，但官方也提醒：外流的金鑰還是能從別的工具拿來用，被擋不等於安全。哪天發現 secret key 出現在頁面、對話紀錄、公開的 GitHub 上，第一件事是到後台把它作廢、換一把新的，再處理別的。
步驟五

預約頁接上 Supabase

要做什麼

在預約頁加上 Supabase 的程式庫，放專案網址和 publishable key；客人按送出時，把表單內容新增到 reservations 表；成功顯示「預約已送出」，失敗顯示看得懂的錯誤，並保留客人填的內容。

跟 Claude 怎麼說

「預約頁接上 Supabase。不要打包，用官方文件寫的 script 標籤從 CDN 載入 supabase-js 第 2 版。只用 publishable key，絕對不要用 secret key。送出時新增一筆到 reservations，不要在新增後面接 select，因為客人沒有讀取的權限。成功顯示『預約已送出，我們會再跟你確認』；失敗用中文說明，表單內容不要清掉。」

「改完先在本機開起來，送一筆測試預約，告訴我後台有沒有多一筆。沒問題再照第七章的方式上傳。」

你自己要動手
  • Claude 可以用 CLI 查到專案網址和 publishable key，不用你去複製。它跟你要的話，從後台 Connect 或 Settings › API Keys 複製 publishable 那一把給它。
  • secret key 不要複製給它。它說需要，問它要拿去哪裡用；答案是「放頁面」，就是做錯了。
  • 上傳後，用自己的手機打開 B 咖啡店的網址，送一筆真的試試看。
做完會看到

按下送出，頁面顯示「預約已送出」。到後台的 Table Editor 打開 reservations，最上面或最下面多了你剛剛那一筆，收到時間是剛剛。

常見卡住的地方
  • 按送出沒反應：多半是程式庫沒載入，或頁面上的程式出錯。請 Claude「用無頭瀏覽器打開頁面，看主控台有沒有錯誤」。
  • 出現 42501：回去看步驟四。授權和規則都要在。
  • 後台有資料，但頁面顯示失敗：常見原因是程式在新增後面接了「把剛新增的那筆讀回來」。客人沒有讀取權限，這一段就會失敗。請 Claude 拿掉，只新增、不讀回。
  • 本機可以，上線後不行：確認上傳的是改過的那一版，再確認頁面裡的專案網址沒打錯。

頁面上加的程式大概是這樣（只列跟資料庫有關的部分）：

<!-- 載入 Supabase 的程式庫（官方文件的寫法，不用打包） --> <script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2"></script> <script> const { createClient } = supabase const db = createClient( 'https://你的專案代號.supabase.co', // 專案網址 'sb_publishable_……' // 可以公開的那把，不是 secret ) const form = document.querySelector('#reserve-form') form.addEventListener('submit', async (e) => { e.preventDefault() const d = new FormData(form) const { error } = await db.from('reservations').insert({ name: d.get('name'), phone: d.get('phone'), reserve_date: d.get('date'), reserve_time: d.get('time'), party_size: Number(d.get('party_size')), note: d.get('note') }) // 有 error 就顯示中文說明；沒有就顯示「預約已送出」 }) </script>

看懂三件事就好：第一行從網路上載入 Supabase 的程式庫；createClient 那段放專案網址和 publishable key；insert 那段把表單的每一格對到表的每一欄。@2 是鎖住第 2 版，避免哪天程式庫大改版，頁面跟著壞掉。

步驟六：怎麼看資料有沒有進來

資料進來了，老闆要看得到。最簡單的方法是 Supabase 後台。

步驟六

在後台看預約，也讓 Claude 幫你查

要做什麼

學會兩種看法：自己在後台 Table Editor 看；或請 Claude 用一句話查出你要的。

跟 Claude 怎麼說

「查 reservations 表，列出明天的所有預約，照時間排，只要姓名、時間、人數。只能讀，不要改任何資料。」

「這週每天各有幾筆預約、總共幾位客人？用表格給我。」

你自己要動手
  • 登入 Supabase 後台，進專案，打開 Table Editor，點 reservations。
  • 在後台你有全部的權限，看得到也刪得掉。看就好，要改要刪，先想清楚。
做完會看到

一張像試算表的畫面，每一列是一筆預約。Claude 查的話，會回你一張整理好的表格。

常見卡住的地方
  • Table Editor 裡看不到剛送的那筆：重新整理一次。還是沒有，回到步驟五看頁面有沒有顯示失敗。
  • Claude 查詢時順手改了資料：每次都講「只能讀」。它要動資料之前，請它先講要改哪幾筆、改成什麼。
店員要看預約，怎麼辦
不要把你的 Supabase 帳號密碼給店員。店員要看今天的預約，比較好的做法是做一個只給店內用的查詢頁，讓店員登入、只看得到今天的預約。這就要用到 Supabase 的會員登入和更細的規則，是下一步的事了。動手前先讀第十四章 功能怎麼切，想清楚這個功能要多大。

步驟七：備份

Supabase 免費版沒有自動備份。官方文件的建議是：免費專案要定期用 CLI 把資料匯出，另外存一份在別的地方。換句話說，資料庫出事時，你手上有幾天前的備份，就能救回到那天；沒有，就沒有。

步驟七

匯出一份，存到別的地方

要做什麼

用 Supabase CLI 把資料庫匯出成檔案（Supabase 的指令叫 db dump），結構和資料各一份，存到你電腦以外的地方。然後定一個固定的頻率。

跟 Claude 怎麼說

「用 Supabase CLI 的 db dump，把 b-coffee-booking 的結構和資料各匯出一份，檔名加今天的日期。查官方文件確認現在的寫法。匯出的檔放在不會推上 GitHub 的資料夾，幫我把這個資料夾加進 .gitignore。」

「寫一份備份步驟說明，存在專案資料夾裡，下次我說『備份預約』你就照做。」

你自己要動手
  • 決定備份要多久做一次。B 咖啡店一週一次可能就夠；預約一天幾十筆，就改成每天。
  • 把備份檔放到你信得過的地方（公司的雲端硬碟、外接硬碟）。備份裡有客人的姓名和電話，是個人資料，不能放在公開的地方。
做完會看到

兩個檔，一個是結構（表長什麼樣），一個是資料（每一筆預約），檔名上有日期。請 Claude 打開資料那份，數一下筆數，跟後台對得上。

常見卡住的地方
  • 指令要你裝別的東西：這個匯出指令在背後要用到 Docker（一個在你電腦上開小隔間跑程式的工具）。請 Claude 說明要裝什麼、為什麼，你同意再裝。
  • 備份檔被推上 GitHub：馬上請 Claude 從紀錄裡移除。只刪檔案不夠，GitHub 的歷史紀錄裡還有。公開的 repo 更要當作已經外流處理。
  • 從來沒試過還原：沒試過還原的備份，不算備份。找一天請 Claude 把備份還原到你的練習專案，看資料齊不齊。

別忘了：一週沒動靜會被暫停

免費專案一週內沒有足夠的資料庫活動，會被暫停。官方的說法是，每天有幾次正常的請求，通常就不會被暫停；但沒有寫明確的門檻。

對 B 咖啡店的意思是：淡季一週沒人預約，專案可能被暫停。暫停的時候，客人按送出會失敗，你不一定會馬上發現。

  • 救回來：登入後台，進那個專案，按 Resume project 確認。資料和設定會回到暫停前的樣子。官方說暫停後一年內都可以在後台恢復。
  • 不想被暫停：升級成付費方案，付費專案不會因為沒動靜被暫停。有真的客人在用、停一天就是損失的時候，這筆錢值得花。
  • 不要用「定時去戳它」的方法硬撐：網路上有人教排程每天自動送請求，避免暫停。這是在跟服務的規則捉迷藏，規則一改就失靈。正式給客人用的，就付費。

另一個選擇：Cloudflare D1

第七章頁面放在 Cloudflare，Cloudflare 自己也有資料庫，叫 D1（SQLite 語法）。資料單純、不需要會員登入時，跟頁面放同一家，少管一個帳號。免費版每個資料庫 500 MB、整個帳號合計 5 GB、每天可以讀 500 萬列、寫 10 萬列（以 Cloudflare 官方頁面為準，查詢日期 2026-11-13）。

跟 Supabase 最大的差別：D1 不能從頁面直接連。頁面要讀寫 D1，得經過一支放在 Cloudflare 上的小函式（Worker）。另外的 REST API 和 wrangler 指令是給你管理資料庫用的，要用帳號的金鑰，不能放進頁面。所以預約頁送出時，是交給這支小函式，小函式檢查完再寫進 D1。門是你（或 Claude）一扇一扇開出來的，每一扇都要自己檢查。用 Supabase 時那套「頁面金鑰加 RLS 規則」，在 D1 這邊換成「小函式裡的檢查」。

這一章用 Supabase 示範，因為它不用多寫一支小函式，B 咖啡店的預約一個晚上就接得起來。要改用 D1，跟 Claude 說：「改用 Cloudflare D1，用 wrangler 開資料庫，寫一支 Worker 接預約頁的送出，在 Worker 裡檢查欄位，再寫進 D1。」兩邊怎麼選，第十一章 技術棧 有比較。

哪裡有邊界

這一章的動作，大部分可以放心交給 Claude。但有幾條線，一定要你自己看過才算數。

最重要的一條：頁面上的金鑰誰都看得到

預約頁上的 publishable key，任何人在瀏覽器按右鍵看原始碼就看得到。這不是漏洞，是本來就這樣設計的。所以把關靠的是資料庫的規則，不是把金鑰藏好。

常見的錯誤想法是：「金鑰藏深一點、拆成兩半、加密一下，別人就找不到。」找得到的。頁面要用它，就得把它送到客人的瀏覽器；送得到客人那裡，就送得到任何人那裡。與其花力氣藏，不如確認規則寫對：這把金鑰被任何人拿去用，最壞能做什麼？照步驟四的設定，答案是「新增一筆預約」，就這樣。

「最壞只能新增一筆」也不是零風險
有人可以寫程式，一秒送一百筆假預約進來。規則擋不了這種事，因為每一筆都是「新增」，都是准的。要擋，得再加一層：例如送出前的人機驗證、同一支電話一天只能預約幾次、或改成經過一支小函式檢查。這已經是「什麼要放在後面檢查」的問題，第十六章 前後端邊界 講怎麼判斷。B 咖啡店剛起步，先跟 Claude 說：「預約頁先加人機驗證；同一支電話一天最多預約三次，這個檢查放在資料庫或小函式裡，不要只寫在頁面上。」

放心交給 Claude，跟一定要你確認的

照頁面的格子開表、寫 SQL、留 Migration 欄位跟頁面一個一個對過；之後每加一欄，它先講為什麼
寫授權和 RLS 規則 它列出的「誰能做什麼」表，只有你要的那幾格打勾；而且它實際測過被擋

  • 「先把 RLS 關掉，比較好測試。」
  • 「用 secret key 比較簡單，權限問題就沒了。」
  • 「我把資料庫重設（reset）一下，重新套用 migration。」對練習專案可以；對有客人資料的專案，資料會不見。
  • 「這個欄位用不到，我把它刪掉。」刪欄位，那一欄的資料跟著沒了。

這幾句都會讓問題「看起來」解決。請它停下來，說明這樣做會影響什麼、有沒有不動資料的做法。

這一章是照著做。後面的章節是讓你自己判斷，什麼時候這樣做會出事：

  • 第十三章 架構拓樸：把頁面、資料庫、外部服務畫成一張圖，看金鑰放在哪一塊、資料的家在哪
  • 第十四章 功能怎麼切：預約之後想加會員、加取消、加提醒，怎麼切才不會越做越黏
  • 第十五章 資料表與欄位：表怎麼拆、欄位怎麼定，為什麼不能讓 Claude 想加就加
  • 第十六章 前後端邊界：什麼可以在頁面上做、什麼一定要放到後面；兩把金鑰的道理在那裡細講
  • 第十七章 會出事的地方：同時預約搶同一個時段、客人連按兩次送出，這類事怎麼先防

這章帶走什麼

  • 資料庫是有規矩的預約簿：會擋錯、會看人、不怕擠。試算表可以當抄本，不要當正本
  • 開專案、登入、付錢是你的事：開表、寫規則、接頁面交給 Claude，你看它列出來的清單
  • 改結構留 Migration：每一次改表都有一張施工單，查得到、重建得了
  • 兩層把關：授權決定門開不開，RLS 決定每一筆准不准。RLS 一定開，只開需要的動作
  • 兩把金鑰：publishable 可以放頁面，secret 絕對不行
  • 頁面上的金鑰誰都看得到：把關靠規則，不是靠藏
  • 免費版沒有自動備份，一週沒動靜會暫停：備份自己做，正式給客人用就考慮付費
  • D1 也行：但要經過一支小函式，不能從頁面直接連
跟 Claude 怎麼說
「預約頁要把資料存進 Supabase。先讀頁面的表單欄位，用 CLI 開 migration 建表。RLS 一定開，先收回這張表原本給頁面的授權，再只授權新增，不准讀、改、刪。頁面只用 publishable key，不准出現 secret key。」
「做完用頁面的金鑰實際測一次：新增、讀取、刪除各試一次，告訴我哪個成功、哪個被擋。」
「列出 Supabase 裡每一張表開放給誰、有沒有開 RLS、規則是什麼。」
「要刪表、刪欄位、清資料、重設資料庫之前，先停下來問我，並說明會少掉什麼。」
「每週幫我匯出一份備份，檔名加日期，不要推上 GitHub。」

到這裡，B 咖啡店有了頁面、有了網址、預約也真的存得下來。這三章是照著做；下一章退一步，看清楚 Claude Code 這個工具本身怎麼用：怎麼讓它記得你的規矩、什麼時候該讓它先想再做，第十章 Claude Code 怎麼用。

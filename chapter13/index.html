第十三章

架構拓樸：先畫出來，才知道哪裡不能亂動

上一章講 API：兩塊之間怎麼傳話、外部服務怎麼接。再往前，第十一章選好了材料：純靜態頁面放 Cloudflare，資料庫用 Supabase 或 D1，動手前先上 GitHub 找現成的。這一章換一個高度：把整個系統有哪幾塊、誰連到誰、資料怎麼流，畫成一張圖。第一章說能改能修靠的是知道邊界，這張圖就是把邊界畫在紙上。

架構拓樸是什麼：一間店的動線圖

比喻：便當店的動線圖。

開一間便當店，裝潢之前會先畫一張平面圖：門口在哪、客人站哪裡點餐、櫃檯在哪、廚房在後面、倉庫放食材和帳本、外送平台的接單機擺哪裡。

這張圖不管便當好不好吃。它只管三件事：店裡有哪幾區、哪一區通到哪一區、東西照什麼路線走。

客人走到櫃檯就停，不會進廚房。鑰匙掛在廚房裡面，不掛門口。帳本只有一本，收在倉庫。這些都跟廚藝無關，是動線。

架構拓樸（Topology）就是系統的這張動線圖。「拓樸」聽起來很硬，意思只是「東西之間怎麼連」。它回答三個問題：

  1. 有哪幾塊？頁面、後端、資料庫，還有哪些別人家的服務。
  2. 誰連到誰？哪兩塊之間有線，哪兩塊之間不該有線。
  3. 資料怎麼流？一張訂單從哪裡進來、經過誰、最後存在哪。

圖上的每一條線，多半就是第十二章 API 講的那件事：一塊向另一塊送出請求，拿回結果。上一章看的是一條線怎麼傳話，這一章看的是全部的線擺在一起長什麼樣子。

把店裡的每一區對到系統裡：

店裡 系統裡 它負責什麼
門口和用餐區 頁面（就是前端，跑在客人的瀏覽器裡） 客人看得到、碰得到的一切
櫃檯和後面的廚房 後端 收單、算錢、決定這件事能不能做
倉庫和那本帳本 資料庫 訂單、客戶、合約都記在這裡
牆上的鬧鐘 排程 時間到自己動：每天早上對帳、合約到期前提醒
外送平台、刷卡機、快遞 外部服務（LINE、金流、寄信） 別人家的服務，你申請來用
放照片和文件的置物櫃 檔案存放處 商品照、合約 PDF、客人上傳的檔案

它跟技術棧不一樣。技術棧（第十一章 技術棧）是選哪個牌子的冰箱、跟哪一家外送平台簽約；拓樸是這些東西擺在哪、怎麼接。牌子之後可以換，動線亂了整間店都要重拉。前端和後端各是什麼，第五章 基本知識講過，這裡不重講；這一章把前端直接叫「頁面」。前後端各該放什麼，第十六章 前後端邊界會細講。

這一章要你會的
不是自己把圖畫得多漂亮，圖可以請 Claude 畫。你要會的是三件事：看得懂一張圖、指得出圖上三個要緊的地方、說得出哪一條線不能畫。
跟 Claude 怎麼說
「先不要寫程式。用一張圖告訴我，這個系統有哪幾塊、誰連到誰」
「這幾塊裡面，哪些是我們自己的，哪些是別人家的服務？」
「用『一張訂單從進來到存好』當例子，把資料走的路線講一遍」

為什麼要先畫：AI 每次只看眼前那一處

Claude 會改，也會修。但你說「這一頁太慢」，它就看這一頁；你說「加一個通知」，它就找最近的地方接上去。這不是偷懶，是你每次交給它的範圍就那麼大。

店裡每次來的都是不同的師傅，沒有人給他平面圖。

今天這位為了少走幾步，在用餐區牆上開一個洞直通倉庫。明天那位嫌櫃檯擠，把外送平台的接單機搬到門口。後天再來一位，從隔壁拉了一條延長線。

每一位都把當天的事做完了，店也照常開。半年後你想換一台冰箱，才發現沒有人知道哪條線接到哪裡。

同一句話，有圖和沒圖，做出來的東西不一樣。假設你說：「訂單成立的時候，通知我的 LINE。」

這樣會出事：沒有圖
它看到的只有訂單頁面那個檔案
最近的做法：頁面送出之後，自己去叫 LINE
LINE 的金鑰跟著寫進頁面

金鑰掛在門口
這樣才對：先讀圖
它先看圖：頁面只通後端，金鑰在後端
做法：後端收到訂單之後，由後端去叫 LINE
圖上多一條「後端 → LINE」，順手更新

兩邊都「做好了」，你在畫面上看不出差別。差別在三個月後。

沒有這張圖，讓 AI 一直改下去會怎樣
每一次都修好了，線卻越拉越多。到最後：

問「客戶資料從哪裡進來、存在哪、有誰在讀」，沒有人答得出來。
想換一家金流或寄信服務，不知道會扯到哪幾塊。
金鑰外流、兩邊數字對不上的時候，不知道從哪裡查起。

這叫耦合：每一塊都跟別塊黏在一起，動一塊就扯到好幾塊。這次黏住的不是幾段程式，是整個系統。出事的樣子，第十七章 會出事的地方會完整講。

線怎麼一條一條變亂，下面有一張可以點的圖，你可以親手加給它看。

跟 Claude 怎麼說
「動手之前先讀架構圖。這次只走圖上已經有的線」
「如果你覺得需要一條新的線，先停下來告訴我為什麼，我同意了再加」

小老闆常遇到的四種形狀

小公司的系統，多半是下面四種形狀其中一種，或是兩三種疊在一起。先認得形狀，Claude 提方案的時候，你才聽得出它打算蓋多大。

四張圖都照我自己的做法畫：頁面用改完直接上傳的純靜態頁面（HTML、CSS、JS），放 Cloudflare；後面接現成的服務，資料庫用 Supabase 或 Cloudflare D1；不自己養機器。為什麼這樣選，第十一章 技術棧講過。

圖上有三種標記，下一節會細講，先認得就好：

  • 對外任何人都碰得到；虛線框是整塊攤開
  • 金鑰金鑰放在這一塊
  • 資料的家這種資料以這裡為準

01只有頁面

店裡的說法：只有櫥窗和一疊傳單。客人看得到，但沒有櫃檯可以收東西。

什麼時候夠用
公司介紹、價目表、活動頁、教學站（這個站就是）。內容是你自己改，客人只看不寫。報價試算這種「算給客人看」的小工具也可以放在這裡。
再長大要加
一旦要「收東西」，例如聯絡表單、報名、預約，就要加一個後端。頁面自己沒辦法把客人交來的資料安全地收好。

02頁面，加一個收表單的後端

店裡的說法：門口多了一個櫃檯。客人把單子遞進來，店員收進抽屜，再喊你一聲。

什麼時候夠用
聯絡我們、活動報名、索取報價、問卷。客人只「交進來」，不需要回頭查自己交過什麼。
再長大要加
客人要登入、要查自己的訂單，或是你要改狀態（已報價、已簽約、已收款）。這時候試算表撐不住，要換成資料庫。

03頁面，加現成的資料庫服務

店裡的說法：倉庫租給專門的倉儲公司管。門禁（誰能進來）和「誰能開哪一格」的規則，也交給它。

這張圖有一條要特別看的線：頁面直接連資料庫。有些資料庫服務（例如 Supabase）就是設計成這樣用，服務本身替你把門：用設在資料表上的存取規則（RLS，第九章「步驟四：開門，再上鎖」動手開過；哪些事規則擋不住、一定要交給後端，第十六章會講）規定「每個人只能讀寫自己的那幾筆」。有些（例如 Cloudflare D1）是給後端程式用的，頁面要讀寫，得先經過一支小函式。兩種都算這個形狀，差別只在圖上有沒有那條直通的線。

什麼時候夠用
會員、訂單、預約、客戶與合約管理、公司內部的後台。大多數「要登入、要記東西」的工具都在這一格。
再長大要加
沒有人開著頁面的時候，系統也要自己動（半夜對帳、LINE 自動回覆），就要加下一種形狀。照片和 PDF 變多的時候，檔案放檔案存放處，資料庫只記「檔案放在哪」。

04要一直待命的：LINE 機器人、排程

店裡的說法：外送平台的接單機，和牆上的鬧鐘。沒有客人走進門，它們也會響。

前三種形狀，都是有人打開頁面才開始動。這一種不是：客人在 LINE 傳一句話，LINE 平台把它轉送到你後端的一個固定網址（這種「別人主動來按你門鈴」的做法叫 Webhook）；或是時間到了，排程去叫醒後端。

「待命」不等於你要養一台二十四小時開著的機器。多半用第十一章說的「門鈴」那種小函式就夠：有人按鈴才醒來。待命的是那個網址。

什麼時候夠用
LINE 自動回覆、每天早上對帳、合約到期前七天提醒、每週寄一份報表。每次醒來做的事不多，幾秒鐘做完。
再長大要加
一次要跑很久的工作，例如大量抓資料、整批處理檔案。這時候才需要一台真的一直開著的機器。它沒人用也照時間計費，還要有人盯著有沒有掛掉，先請 Claude 說明為什麼小函式做不到。怎麼判斷要不要這台機器，第十一章 技術棧有講。
這種形狀容易漏掉的一件事
那個固定網址是對外的，任何人都可以對它送東西，假裝自己是 LINE。後端收到之後要先確認「這真的是 LINE 送來的」（LINE 會在每一次轉送附上簽章，讓後端核對），才往下處理。
動手之前，先找現成的
預約系統、報價單產生器、LINE 機器人，這些多半有人做過。怎麼找、怎麼判斷能不能用，照第十一章 技術棧的「先上 GitHub 找」。找到之後多做一件事：請 Claude 畫出那個專案的拓樸，是上面哪一種形狀、金鑰放哪、資料存哪。形狀跟你要的對得上，再往下看。
跟 Claude 怎麼說
「我要的只是聯絡表單，客人只會交資料進來。用『頁面加一個收表單的後端』就好，不要加資料庫和登入」
「頁面用純靜態、不要打包，後面接現成的服務。先告訴我你打算用哪一種形狀、為什麼」
「你的方案比我講的多了哪幾塊？每一塊不加的話會怎樣？」
「先上 GitHub 找有沒有現成的。找到的話，把它的架構畫給我看再決定」

圖上一定要標的三件事

一張圖只畫了方塊和線，還不夠用。要多標三件事，這張圖才擋得住人。上面四張圖的三種標記，就是這三件事。

一、哪一段是對外的

對外，是指任何人都碰得到。碰得到有兩種程度：

  • 頁面是整塊攤開的。它跑在客人的瀏覽器裡，裡面寫了什麼，會看原始碼的人全部看得到。
  • 後端只有窗口對外。誰都可以來敲那個網址，但看不到裡面。上一節的 Webhook 網址也是這一種。

店裡的說法：用餐區誰都能走進來東看西看；櫃檯誰都能來問，但進不了廚房。兩種都要假設有人會亂試，差別是用餐區連藏東西的地方都沒有。

二、金鑰放在哪一塊

金鑰是你跟外部服務之間的鑰匙：LINE 一把、金流一把、寄信一把。誰拿到，誰就能用你的名義發訊息、花你的額度。

每一把金鑰，都要在圖上標出它放在哪一塊。標完看一眼：金鑰只能放在外人看不到裡面的那幾塊。出現在頁面上，就是警報。店裡的鑰匙掛在廚房裡面，沒有人會掛在用餐區的牆上。（例外：Supabase 給頁面用的 publishable key 本來就設計成可以公開，資料靠存取規則把關；另一把 secret key 會略過所有規則，絕對不能出現在頁面上。細節在第十六章 前後端邊界。）

三、哪一塊是資料唯一的家

訂單、客戶、合約，每一種資料指定一個家。別的地方要用，就來這裡問，不要各自抄一份。工程師叫它單一資料來源（SSOT），搬到圖上就是一個標記。抄成兩份會怎麼出事，第十七章 會出事的地方有實例。

店裡的說法：帳本只有一本。櫃檯一本、廚房一本、老闆手機裡又一本，月底一定對不起來。

這樣會出事：只畫方塊和線
頁面 → 後端 → 資料庫 後端 → LINE 後端 → 試算表 看得出誰連到誰，但答不出： 金鑰在哪？ 訂單以資料庫還是試算表為準？ 外人碰得到哪幾塊？
這樣才對：三件事都標了
頁面（對外） → 後端（對外的只有收訂單的窗口； 　LINE 的金鑰在這） → 資料庫（訂單、客戶的家） 後端 → LINE 後端 → 試算表（抄本，每天重抄） 三個問題，看圖就答得出來
跟 Claude 怎麼說
「在圖上標三件事：哪幾塊是對外的、每一把金鑰放在哪一塊、每一種資料的家是哪一塊」
「訂單、客戶、合約，各自以哪一塊為準？有沒有哪一種資料現在有兩個家？」
「頁面這一塊裡面，有沒有出現任何金鑰？」

邊界：哪些線可以畫，哪些不能畫

標完三件事，邊界就看得出來了。平面圖上有牆：不是每兩區之間都該開一扇門。系統也一樣，下面四條是常用到的牆。

  1. 對外的頁面，不拿金鑰去連外部服務。要發 LINE、要收款、要寄信，都請後端代辦。
  2. 兩塊之間只留一條明確的通道。頁面要拿訂單，全部走同一個窗口。不要這一頁走後端、那一頁自己繞過去。
  3. 寫進資料的家，只有一條路。誰能新增、誰能改訂單，都經過同一個地方把關。
  4. 外部服務回頭找你，只找後端。付款結果、LINE 訊息，都送到後端，不送到頁面。
這條線 可以畫嗎 為什麼
頁面 → 後端 可以 客人走到櫃檯，本來就該走這條
後端 → LINE、金流、寄信 可以 金鑰在後端，由後端去叫
排程 → 後端 可以 鬧鐘響了，叫店員去做，走的還是原本那條路
頁面 → LINE、金流、寄信（帶著金鑰） 不行 金鑰到了門口，誰都拿得走
金流 → 頁面（付款結果只告訴頁面） 不行 客人把視窗關掉，就沒人知道他付了；頁面說「我付了」也不能算數
排程 → 自己另存的一份名單 不行 資料多了第二個家
頁面 → 資料庫 看情況 資料庫服務有開存取規則才可以，見下面的灰色地帶

灰色地帶：線也畫不到百分之百乾淨

四條牆是原則。實際的圖上，總有幾條線不那麼乾淨：

  • 頁面直接連資料庫。前面的第三種形狀就是。這條線可以畫，但要在線上註明「靠存取規則把關」，而且金額、狀態這類不能讓客人自己說了算的東西，還是交給後端寫。規則沒開，就等於倉庫沒鎖。
  • 頁面嵌了別人家的東西。影片、地圖、客服小視窗，頁面會直接連到別人家。這種線沒帶你的金鑰，也不碰你的資料，可以畫。但圖上照樣要有，不然哪天頁面變慢，你不知道是誰拖的。
  • 為了快，多存一份。報表每次重算太慢，另外存一份算好的。這是第二份，不是第二個家：圖上寫明「抄本，以資料庫為準，每天重抄」，就不會有人拿它來做決定。
分不清楚能不能畫的時候，問這兩句
「外人順著這條線走進來，會碰到什麼？」
碰到的只有本來就公開的東西：可以。碰到金鑰、別人的資料、能改金額的地方：不行。

「這一份跟那一份不一樣的時候，以誰為準？」
答得出來，而且圖上寫了：可以留。答不出來：先別加。
跟 Claude 怎麼說
「頁面只能連我們自己的後端。要用 LINE、金流、寄信，一律由後端去叫」
「頁面跟後端之間只留一個窗口。要開第二條路之前先問我」
「付款結果由金流直接通知後端，不要靠付款成功頁回報」
「這條線如果是例外，在圖上註明為什麼可以、靠什麼把關」

動手玩：一張訂單走過哪些地方

下面是一個小店的訂單系統，照前面的邊界畫好的。先按「客人送出一張訂單」，看資料照什麼順序走。再按幾次「讓 AI 隨便加一條線」，每按一次，就是你提了一個很平常的要求，而它挑了最近的路。

這張圖只在你眼前這一頁運作，不會送出任何資料。

按鈕要開 JavaScript 才會出現。看不到的話，圖下面兩份清單是同一件事的文字版。

一張訂單走的路
  1. 頁面把「選了什麼、幾個」交給後端。進來的路只有這一條。
  2. 後端自己查價目、算金額，把訂單寫進資料庫。
  3. 後端帶著金鑰，請金流開一筆付款。客人付完，金流回頭通知後端。
  4. 後端把資料庫裡的那張訂單改成「已付款」。
  5. 後端通知你的 LINE，再請寄信服務寄確認信給客人。
AI 加上去的線
  1. 你：「查訂單的那一頁太慢。」它讓頁面跳過後端，自己去資料庫拿。對外的地方多了一條通到資料的路，路上沒有人檢查這位客人能看哪幾筆。
  2. 你：「客人一送出就要通知我。」它把 LINE 的金鑰寫進頁面，由頁面直接發。金鑰到了任何人都看得到的地方。
  3. 你：「每天給我一份報表。」它把訂單另外抄一份到試算表。訂單有了第二個家，圖上沒有寫以誰為準。
  4. 你：「還沒付款的，寄信催一下。」它拿試算表那一份來判斷誰沒付。抄本晚一步更新，付過錢的客人也收到催繳信。

四條線都不是誰寫壞的。每一條都對應一個合理的要求，也都當場「做好了」。亂掉的原因只有一個：加線的那一刻，沒有人拿圖出來對。

這章帶走什麼

  • 系統先畫成一張圖：有哪幾塊、誰連到誰、資料怎麼流。圖請 Claude 畫，你負責看懂。

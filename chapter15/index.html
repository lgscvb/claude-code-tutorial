第十五章

資料表與欄位：資料的家要先蓋好

資料的家要先蓋好。第九章你已經開過一張預約表，存進第一筆資料；上一章又把功能切成一塊一塊，每一塊都要讀寫資料。這一章講表要怎麼設計，才不會越加越亂。你說一句「再記一個⋯⋯」，Claude 就加一欄；半年後，同一位客戶的電話有三個地方在存，沒有人知道哪一個才對。這一章不教你寫 SQL，教你看懂資料放在哪、為什麼這樣放，以及它動手之前你該問哪三句。

畫面可以重做，資料不行

網頁的畫面做壞了，請 Claude 重做一版，舊的丟掉就好。資料不一樣。裡面已經躺著半年的客戶、合約、收款紀錄，結構一開始排錯，之後每改一次都是帶著全部家當搬家。

第十三章 架構拓樸說，每一種資料要有一個家。這一章走進那個家，看裡面的表和欄位怎麼排。你不用自己設計資料庫，但要看得懂它的設計，才知道哪裡不能讓 AI 隨手加東西。這就是本書一直講的「知道邊界」，落在資料上的那一段。

這一章要帶走三件事：

  • 看得懂：資料表、欄位、表和表之間的線。
  • 會判斷：一份資料設計，哪裡以後會出事。
  • 知道邊界：它要加欄位、開新表之前，你問得出那三句話。

表與欄位：檔案櫃、抽屜、表單上的格子

比喻：辦公室的檔案櫃。

一座檔案櫃有好幾個抽屜。第一個抽屜只放「客戶資料表」，第二個只放「合約」，第三個只放「收款單」。不會有人把收款單塞進客戶那個抽屜。

同一個抽屜裡的表單都是同一種格式：印好的格子，名稱一格、電話一格、狀態一格。每張表單右上角有一個流水號，整個抽屜不重複。

資料庫就是這座檔案櫃。整章都會回到這座櫃子。

你用過 Excel 的話，其實已經懂一半了。三種說法對起來是這樣：

檔案櫃 Excel 資料庫的叫法
整座檔案櫃 一個 Excel 檔 資料庫（Database）
一個抽屜 一張工作表 資料表（Table）
表單上印好的格子 最上面那一列的欄名 欄位（Column）
一張填好的表單 一列 一列資料，也叫一筆紀錄（Row）
右上角的流水號 沒有，要自己編 主鍵（Primary Key）

打開「客戶」那個抽屜，裡面長這樣。表名和欄位名照慣例用英文小寫：

id name phone status created_at
1 A 設計工作室 0912-000-001 active 2026-01-08
2 B 咖啡店 0912-000-002 active 2026-02-14
3 C 補習班 04-0000-0003 inactive 2026-03-03

這張表叫 customers。status 那一欄的 active 是「往來中」，inactive 是「已停用」。這種固定選項，資料庫裡多半存英文代號，畫面上再換成中文給人看。

跟 Excel 差在哪

差兩件事。

第一，格子有規定。Excel 的「金額」那一欄，你打「三萬」「30,000」「約 3 萬」它全收。資料庫的金額欄位先講好只收數字，打「三萬」會被退回來。麻煩在前面，省事在後面：之後要加總、要排序，不會被一格「約 3 萬」卡住。

第二，表和表之間有正式的連結。Excel 裡你用眼睛對「這張合約是哪位客戶的」。資料庫裡這條線是明寫的，下一節講。

主鍵：每張表單的流水號

主鍵（Primary Key）是每一列的身分：整張表不重複，發了就不改。通常是一欄叫 id 的編號，由資料庫自動發，你不用管它是幾號。

不要拿「有意義的東西」當主鍵。電話會換，公司名會改，個人客戶沒有統一編號。編號什麼意思都沒有，所以永遠不用改。

跟 Claude 怎麼說
「現在這個專案有哪些資料表？每張表用一句話說明它放什麼」
「每張表都要有自動編號的 id 當主鍵，不要用電話、名字、統編當主鍵」

表和表怎麼連：用編號，不用名字

整章用同一組例子。你接案子，手上有三種東西：客戶、合約、付款。

  • 一位客戶可以簽很多張合約。
  • 一張合約可以分很多次付款。

這種關係叫一對多（One-to-many）。檔案櫃的做法你早就會了：合約上不會把客戶的電話地址整份再抄一遍，只留一格寫「客戶編號：1」。要看這位客戶的資料，拿著編號去客戶那個抽屜翻。

關聯圖：一位客戶對多張合約，一張合約對多筆付款。「多」的那一邊，多一欄記「一」的那一邊的編號。

合約表的 customer_id、付款表的 contract_id，這種「記著別張表編號」的欄位叫外鍵（Foreign Key）。

注意付款表沒有 customer_id。這筆錢是誰付的？順著線走：付款 → 合約 → 客戶。順著線走得到的，就不用再存一份。

為什麼用編號連，不用名字連

這樣會出事：合約上寫客戶的名字
合約 101｜客戶：A 設計工作室
合約 102｜客戶：A設計工作室

少一個空格，被當成兩位客戶。
客戶改名成「A 設計有限公司」，舊合約全部找不到主人。
兩位客戶剛好同名，合約混在一起。
這樣才對：合約上寫客戶的編號
合約 101｜customer_id：1
合約 102｜customer_id：1

名字只存在客戶表一個地方，改一次全部跟著對。
編號不會多一個空格、不會同名、不會改。

外鍵設好之後，資料庫還會幫你看門。合約上寫「客戶編號 99」，客戶表沒有 99 號，資料庫直接拒收。Supabase 用的 PostgreSQL 和 Cloudflare D1 都會照外鍵擋。用名字連沒有這道門，打錯字照樣存得進去。

還有一種：多對多
一張合約包好幾個服務項目，同一個服務項目也出現在很多張合約。兩邊都是「多」，一欄編號記不下來，中間要多一張表（例如「合約項目」），每一列記「哪張合約、哪個項目、多少錢」。

看到 Claude 開了一張名字像 contract_items 的表，多半就是這個用途。
跟 Claude 怎麼說
「表和表之間一律用 id 連，不要用名字或電話去比對」
「外鍵要設起來，指到不存在的客戶要被資料庫擋下來」
「畫一張關聯圖給我：哪張表的哪一欄，連到哪張表」

動手玩：點一位客戶，看線怎麼走

下面是三張表裡的資料。先點一位客戶，看線怎麼一路走到付款。再切到「用名字連」，按一次改名，看同一批資料會發生什麼事。

這些都是示範用的假資料，只在你眼前這一頁運作，不會送出任何東西。
customers 客戶
點一位客戶
contracts 合約
記著客戶的編號

這個示範要開 JavaScript 才能點。看不到按鈕的話，下面是同一件事的文字版。

客戶 1　A 設計工作室
├─ 合約 101　年度網站維護
│　　├─ 付款 501　18,000 元
│　　└─ 付款 502　18,000 元

從客戶 1 出發：2 張合約、3 筆付款，共收 76,000 元。

現在客戶 1 改名成「A 設計有限公司」：

用名字連
合約上寫的還是舊名字「A 設計工作室」
用新名字去找，一張都找不到

2 張合約、3 筆付款還在資料庫裡，只是沒有人找得到。線斷了。
用編號連
合約上寫的是 customer_id：1

兩個版本的資料一模一樣。差別只有合約上那一格寫的是「1」還是「A 設計工作室」。這一格是設計資料表那天決定的，之後所有功能都踩在它上面。名字會撞名、會多空格、會改；編號不會。

跟 Claude 怎麼說
「合約表是用什麼連到客戶表的？編號還是名字？」
「找出所有拿名字、電話、Email 比對來連資料的地方，列給我，先不要改」

欄位怎麼定：一格只放一種東西

回到表單。印表單的人要先決定兩件事：有哪些格子、每個格子可以填什麼。

一格只放一種東西

「聯絡方式」不是一種東西。「手機」是，「Email」是，「LINE ID」是。判斷方法：你之後會不會想單獨用它來找、排序、加總？會，就該自己一格。

那「地址」要不要拆成縣市、區、路？看你用不用得到。要統計「台中的客戶有幾位」就拆；只是印在信封上就不用。這裡沒有百分之百乾淨的答案，切到你會用到的細度就停。

每個格子可以填什麼：型別

格子的規定叫型別（Data type）。常見的就這幾種，第二欄是 PostgreSQL（Supabase 用的那種資料庫）的寫法，看到認得就好。Cloudflare D1 用的是 SQLite 那一套，型別的叫法不太一樣，道理相同：

白話 常見寫法 放什麼 要注意
文字 text 名稱、備註、電話、統編 電話、統編、郵遞區號是文字，不是數字。開頭的 0 不能掉，也不會拿來加減。
整數 integer
bigint		 數量、次數、編號 沒有小數點。
金額 integer
numeric		 合約金額、付款金額 台幣用整數存到「元」；要小數的用 numeric。不要用 float 這一類，下一節的坑四會講。
日期 date 簽約日、到期日 只記哪一天。
日期時間 timestamptz 建立時間、付款時間、收到預約的時間 存成一個不會因時區搞錯的時間點：內部存成國際標準時間（UTC），顯示時再換成你的時區。
幾點 time 營業時間、預約的時段 只記幾點幾分，不含哪一天。第九章的預約表就是日期一欄、時間一欄。
是或否 boolean 要不要開發票 只有兩種答案才用。三種以上，用下面講的「狀態」。

還有一個會一直遇到的字：NULL，意思是「這格還沒填」。它跟 0、跟空白文字都不一樣：付款金額是 0，代表收了零元；是 NULL，代表還不知道。哪些格子不准空著（必填），也是設計的一部分。

每張表都該有的三個欄位，加一個常用的

欄位 白話 沒有它會怎樣
id 編號 沒辦法指著某一列說「就是這一筆」，別張表也連不過來。
created_at 建立時間 「上個月新增幾位客戶」答不出來。
updated_at 最後修改時間 資料怪怪的時候，查不到是什麼時候被動過。
status 狀態（會換狀態的表才要，例如客戶、合約、預約） 只能靠刪除來表示「不要了」，或是長出一排是或否的欄位。

狀態用一欄，不要用一排開關

這樣會出事：一排是或否
is_signed　　已簽約：是
is_cancelled　已作廢：是
is_expired　　已到期：否

已簽約又已作廢，現在到底算哪一種？三個開關有八種組合，其中好幾種根本不該存在。
這樣才對：一欄 status
status 只能填這四種：
draft（草稿）、active（進行中）、
ended（已結束）、void（已作廢）

一張合約同一時間只會在一種狀態。清單先講死，填別的會被擋。

同一個東西，只叫一個名字

這張表叫 customer_id，那張表叫 client_id，再一張叫 member_id，指的都是客戶。半年後連 Claude 都會以為這是三種人。開工那天先定下來：我們叫「客戶」，英文一律 customer。

跟 Claude 怎麼說
「這一欄打算用什麼型別？為什麼？」
「狀態用一個 status 欄位。先列出所有可能的值給我確認，不要開一排是或否的欄位」
「每張表都要有 id、created_at、updated_at」
「這個專案裡『客戶』一律叫 customer，不要 client、member、user 混著用」

常見的五個坑

下面五個，是請 AI 做系統常看到的。每一個剛發生的時候都不會壞，畫面照樣正常，所以才危險。

坑一：一格塞好幾個值

這樣會出事
合約 101｜服務項目：網站維護、主機、網域
合約 103｜服務項目：主機代管，網域

「買了主機的客戶有哪些？」只能拿文字去比，「主機」和「主機代管」算不算同一個？
「每個項目各賣多少？」算不出來，金額沒有拆。
這樣才對
另開一張「合約項目」表，一個項目一列：

合約 101｜網站維護｜24,000
合約 101｜主機　　｜ 9,000
合約 101｜網域　　｜ 3,000

要數、要加總、要改其中一項，都是對「一列」動手。

認法很簡單：一格裡面出現頓號、逗號、換行，就該問一句。

坑二：同一筆資料存兩個地方

這樣會出事
客戶表有 phone
合約表又抄一份 contact_phone
合約表還有一欄 paid_amount（已收金額）

客戶換電話，只改到客戶表，合約頁還是舊號碼。
補登一筆付款，忘了改已收金額：合約說收了 18,000，付款表加起來是 36,000。
這樣才對
電話只放客戶表
已收金額不存

合約頁要顯示電話，順著 customer_id 去客戶表拿。
要看收了多少，把這張合約的付款加起來。

原則只有一句：同一筆資料只存一個地方，這叫單一資料來源（SSOT）。落到資料表上，可以記成一句：查得到的不存，算得出來的不存。為什麼一份資料存兩個地方遲早會出事，第十七章 會出事的地方會整個攤開講。

看起來重複，其實不是：留底
合約金額是簽約那天講定的數字。之後你的價目表漲價，舊合約不該跟著變。所以合約上自己記一份金額是對的，那是「當時的事實」，不是抄一份。

分辨方法只有一句：來源改了，這一格該不該跟著變？
該跟著變的（客戶電話）：只存一處。
不該跟著變的（簽約金額、開發票當下的抬頭）：留底。

所以「不重複」沒辦法照字面做到百分之百，要一格一格問。

坑三：用名字當關聯

上面的示範玩過一次了。同樣的事不只發生在客戶名稱上。付款表記「合約名稱：年度網站維護」，明年同一位客戶又簽一張同名的，這筆錢算哪一年的？用 LINE 的顯示名稱認會員，客人換個暱稱就變成一位新客人，點數歸零。

改法一樣：付款表記 contract_id；會員表記 LINE 平台給的使用者 ID，暱稱隨他換。

原則：拿來連的那個東西，必須不會變、不會重複。名字、電話、Email、暱稱，四個都會變。

坑四：金額用會有小數誤差的型別

電腦有一種存小數的方式叫浮點數（float）。它算得快，但很多小數只能存成「很接近」的值。

這樣會出事：金額用 float、real、double precision
0.1 + 0.2
= 0.30000000000000004

一筆只差一點點。幾千筆加起來、再四捨五入，報表和發票差一塊錢，會計來問你。
這樣才對：integer 或 numeric
台幣：用整數存到「元」
18000 + 18000 = 36000

要小數的（外幣、稅率）：用 numeric
0.1 + 0.2 = 0.3

存多少就是多少。

這不是本書自己的偏好。PostgreSQL 官方文件也寫：金額這種要算準的東西，用 numeric，不要用 real、double precision 這類浮點數。

型別選對了還有一件事要講好：稅金、折扣在哪一步四捨五入。這種會影響錢的計算要放在後端，不能交給畫面上的 JavaScript，第十六章 前後端邊界會講。

坑五：刪除直接把資料抹掉

這樣會出事：真的刪掉
你：「把這位客戶刪掉」

下場一：他名下還有合約，
資料庫擋下來，畫面跳錯誤。

下場二：Claude 為了讓刪除「成功」，
設成連帶刪除（ON DELETE CASCADE）。
客戶一刪，他的合約、付款紀錄整串消失。去年的營收少了一塊，救不回來。
這樣才對：改狀態
status 改成 inactive（已停用）
或加一欄 deleted_at 記下停用的時間

清單預設只列往來中的客戶。舊合約、舊帳都還在，報表對得起來。按錯了，改回來就好。

這種「標記成不要了，但資料還在」的做法叫軟刪除（Soft delete）。

真的要刪的情況也有，例如客人要求刪掉他的個人資料。那是你本人要點頭的決定：哪些連帶的紀錄該留、該怎麼處理，先問清楚再做。不該是 AI 為了修掉一個錯誤訊息，順手做的。

跟 Claude 怎麼說
「檢查現在的資料表：有沒有哪一欄一格裡塞了好幾個值？」
「有沒有哪些欄位的內容，其實可以從別張表查到或算出來？列給我，先不要改」
「所有金額欄位是什麼型別？有 float、real、double precision 的列出來」
「刪除一律做成軟刪除。不要用 ON DELETE CASCADE，除非先問過我」

AI 一直加欄位，半年後會怎樣

Claude 每次只處理你眼前講的那一件事。對它來說，加一欄很省事：不用先讀懂舊的結構，不會弄壞現有的功能，馬上能交差。所以它傾向於「加」，不傾向於「整理」。

  1. 第 1 週
    你：「客戶要記電話」客戶表多一欄 phone。
  2. 第 3 週
    你：「合約頁也要看到聯絡電話」合約表多一欄 contact_phone，把電話抄了一份。
  3. 第 7 週
    你：「再記一個客戶的 LINE」客戶表多一欄 line。過一陣子你換個說法又講了一次，又多一欄 line_id。
  4. 第 12 週
    你：「要看得出這張合約收款了沒」合約表多一欄 is_paid。可是付款表早就在了。
  5. 第 18 週
    你：「有客戶要分期」合約表再多一欄 paid_amount。
  6. 半年後
    你：「這張合約到底繳清了沒？」is_paid 說繳清了，paid_amount 說還差一萬，付款表加起來是第三個數字。

沒有哪一步是錯的，每一次都「做好了」。合起來，同一件事有三個答案，而且沒有人記得哪一個才算數。不同頁面各讀各的欄位，改一處要記得另外兩處，越改越難維護，工程師叫這個「耦合」。Claude 也不記得：它下次開新對話，看到三欄都在，三欄都可能拿來用。

加欄位之前，問這三句

01這個東西，已經有地方放了嗎？

先找。有，就用現有的；現有的不夠用，就改現有的。不要在旁邊再開一欄差不多的。

02它屬於哪一張表？

問「它在描述誰」。電話描述客戶；簽約日描述合約；匯款帳號末五碼描述某一次付款。

拿不準就用這個測試：這位客戶有兩張合約的時候，這個東西有一個還是兩個？一個，放客戶表；兩個，放合約表。

03加了以後，哪些功能要跟著改？

新增的表單、編輯頁、清單、匯出的報表、誰看得到。只加欄位不改這些，那一欄永遠是空的；改了一半，就是下一個對不起來的地方。

這三句，你不會寫程式也問得出來，答案你也判斷得了。這就是你守的邊界。

不是不准加
新的事實本來就該有新的欄位，例如以前沒記過的統一編號。要擋的是同一件事的第二個存放處。
跟 Claude 怎麼說
「加欄位之前先回答三件事：現在有沒有欄位已經在放這個？它該放哪一張表、為什麼？加了以後哪些頁面和功能要跟著改？我確認了你再動」
「如果現有的欄位可以用，就用現有的，不要新增」
「is_paid、paid_amount 和付款表講的是同一件事。以付款表為準，另外兩欄列出還有哪裡在用，先不要刪」

拿第九章的預約表練一次

上面講的都是客戶、合約、付款。換成你在第九章 資料庫替 B 咖啡店開的那張 reservations（預約）表，同一套問法照樣用得上。

第九章那張表是一張放全部：姓名、電話、預約日期、預約時間、人數、備註，再加上每筆的編號和收到的時間。起步這樣完全沒問題，你的表沒有做錯。等熟客回來第五次，事情就來了：

一張表放全部：熟客來了五次
reservations：預約 1｜D 小姐｜0912-000-002｜11/02｜14:00｜2 位
reservations：預約 2｜D 小姐｜0912-000-002｜11/09｜15:30｜4 位
reservations：預約 3｜D小姐 ｜0912-000-020｜11/16｜14:00｜2 位
⋯⋯

她換了電話，舊的四筆還是舊號碼。
名字少一個空格、電話打錯一碼，「她來過幾次」就數不準。
拆成兩張：客人一張、預約一張
customers：id 7｜D 小姐｜0912-000-002

reservations：預約 1｜customer_id：7｜11/02｜14:00｜2 位
reservations：預約 2｜customer_id：7｜11/09｜15:30｜4 位
reservations：預約 3｜customer_id：7｜11/16｜14:00｜2 位

電話只存一處，改一次就對。來過幾次，數 customer_id 就好。

判斷就是前面那一句：這位客人有兩筆預約的時候，電話有一個還是兩個？一個，所以姓名、電話屬於客人，不屬於預約。日期、時間、人數、備註每一次都不一樣，屬於預約。拆完以後，reservations 少了 name、phone 兩欄，多了一欄 customer_id。

拆表不是只動表。第九章的預約頁是沒登入的客人直接寫進 reservations，而且只開了「新增」；客人讀不到 customers，也就不知道自己是幾號。所以要拆的那天，送出預約的路也要跟著改：交給後端先找到或建好這位客人，再寫進預約。什麼一定要放後端，第十六章 前後端邊界會講。

其他幾件事也一樣套得上：

  • 狀態：第九章的表還沒有這一欄。要加的時候，已預約、已完成、已取消、沒來，用一欄 status，不要開 is_cancelled、is_done 一排開關。
  • 取消：改狀態，不要真的刪掉。不然「上個月取消了幾筆」答不出來。
  • 日期和時間：第九章拆成兩欄，reserve_date（date）和 reserve_time（time），剛好對上預約頁的日期格和時間格。B 咖啡店只有一家店、都在同一個時區，這樣好懂，照用就好。合成一欄日期時間（timestamptz）的好處是一格就是一個確定的時間點，算「兩小時後」、跨時區都不容易錯；等到要開別的時區的分店、或要算兩個時段有沒有重疊，再請 Claude 評估要不要換。不管哪一種，都不要用文字存「下週三下午」。

不過，不一定要一開始就拆。小店剛起步、客人很少重複，一張表先用著也行；等你開始想問「這位客人來過幾次」，就是該拆的時候。這裡一樣沒有百分之百乾淨的答案，要拆的那天，照下面講的寫成 migration，不要讓 AI 直接改正式的資料。

兩位客人同時搶最後一個時段，誰算數？那是另一種會出事的情況，不是表怎麼切的問題，第十七章 會出事的地方會講。

跟 Claude 怎麼說
「我們的預約表裡，有哪些欄位其實是在描述客人、不是在描述這一次預約？列給我，先不要改」
「如果要把客人拆成一張表，給我看 migration 的內容，還有舊的預約資料要怎麼對到新的客人編號」
「拆完以後，預約頁送出時要怎麼找到或建好客人？哪一段要放後端、為什麼？先講給我聽，不要改」

SQL：讀得懂就好

SQL 是跟資料庫講話用的語言，附錄：術語字典裡也查得到。你不用自己寫，Claude 會寫。你要做到的是，它寫完之後看得出兩件事：它去了哪幾張表、它是在看資料還是在改資料。

讀法：先找大寫的字。下面五個例子都用前面那三張表。

SELECT … FROM：從哪個抽屜，拿哪幾格

SELECT name, phone FROM customers;

白話：從客戶表，把每一位的名稱和電話拿出來。SELECT * 的星號是「每一格都要」。單純的 SELECT 只看不改，不會動到資料。

WHERE：只要符合條件的

SELECT id, title, amount FROM contracts WHERE customer_id = 1 AND status = 'active';

白話：從合約表，只拿「客戶編號是 1、而且狀態是進行中」的那幾張，列出編號、名稱、金額。

JOIN：把兩個抽屜的表單對起來

SELECT customers.name, contracts.title, payments.amount, payments.paid_at FROM payments JOIN contracts ON contracts.id = payments.contract_id JOIN customers ON customers.id = contracts.customer_id WHERE payments.paid_at >= '2026-09-01';

白話：從付款表出發。每一筆付款，用 contract_id 找到它的合約，再用合約的 customer_id 找到客戶。只要九月一日以後的。結果每一列是「誰、哪張合約、付了多少、什麼時候」。

讀 JOIN 只要盯著 ON 後面那一句：是不是「編號 = 編號」。看到 ON customers.name = contracts.customer_name 這種拿名字對的，就是坑三。

INSERT：放一張新表單進去

INSERT INTO payments (contract_id, amount, paid_at) VALUES (101, 18000, '2026-09-05 14:30');

白話：付款表新增一列：101 號合約、收 18,000 元、九月五日下午兩點半。前面括號是格子名稱，VALUES 後面是照同樣順序填進去的值。沒寫到的 id 和 created_at，由資料庫自己填。

UPDATE：改某一張表單上的格子

UPDATE customers SET name = 'A 設計有限公司', updated_at = now() WHERE id = 1;

白話：客戶表裡編號 1 的那一位，名稱改掉，順便記下修改時間。

UPDATE 和 DELETE，第一件事是找 WHERE
上面那一段少了最後一行 WHERE id = 1，意思就變成「每一位客戶的名稱都改成 A 設計有限公司」。資料庫不會問你確不確定。

DELETE 也一樣：DELETE FROM customers; 是把整張客戶表清空。

看到 UPDATE 或 DELETE，先找 WHERE。找不到，先喊停。

一張表看完：它是在看，還是在改

開頭的字 在做什麼 你要多小心
SELECT 看資料 單純的 SELECT 不會改到東西
INSERT 新增一列 會多出資料，看它加到哪張表
UPDATE 修改現有的列 找 WHERE，確認改到的是哪幾筆
DELETE 刪掉現有的列 找 WHERE，而且先問能不能改成軟刪除
CREATE TABLE
ALTER TABLE
DROP TABLE		 改的是結構：開新表、改欄位、整張表丟掉 下一節講，這種要留紀錄

「單純」兩個字是有原因的。整段是 WITH 開頭、中間夾著 UPDATE 或 DELETE，或是 SELECT 後面在叫一個專案自己寫的資料庫函式（名字後面帶括號），看起來是 SELECT，還是可能改到資料。看到這兩種，請 Claude 先講清楚會不會改。

跟 Claude 怎麼說
「這段 SQL 用白話講一次：從哪幾張表、拿哪些欄位、條件是什麼、會不會改到資料」
「這一句會改到資料嗎？會改到幾筆？先用 SELECT 把會被改到的那幾筆列給我看」
「UPDATE 和 DELETE 都要有 WHERE，沒有的不要執行」

改結構要留紀錄：Migration

回到檔案櫃。

客戶資料表要多印一格「統一編號」。你不會拿筆在抽屜裡每一張舊表單上自己畫格子。正規做法是發一張改版通知：哪一天、哪一種表單、多了哪一格、舊表單這一格先空著還是補什麼。

通知單照順序收在一個夾子裡。新來的同事把夾子從頭翻到尾，就知道現在的表單為什麼長這樣。

Migration 就是這個夾子：資料結構的修改紀錄。每改一次結構，專案資料夾裡就多一個檔案，裡面是那一次要執行的 SQL，照順序排好。一個 migration 檔的內容大概長這樣：

-- 客戶表加一格「統一編號」 ALTER TABLE customers ADD COLUMN tax_id text;

白話：客戶表多一欄 tax_id，型別是文字。舊客戶這一欄先是 NULL。

這些檔案放在哪，看你用什麼。用 Supabase 的專案在 supabase/migrations/，用 Cloudflare D1 的預設在 migrations/。你不用背，知道「專案裡有一個資料夾專門放這個」就夠了。

為什麼不能請 AI 直接在正式的資料上改

Claude 連得到資料庫的時候，省事的做法是直接對正式的那一份下指令。當下會動，後面有四個麻煩：

  • 沒有紀錄。三個月後多了一欄，沒有人知道是哪天、為了什麼加的。
  • 兩邊對不起來。正式的資料庫改了，測試用的那一份沒改，或是反過來。程式在一邊跑得動，另一邊壞掉。
  • 下一個對話不知道。新開的 Claude 是從專案資料夾裡的檔案認識結構的。改動沒寫成檔案，它看到的就是舊的。
  • 有些動作回不來。刪欄位（DROP COLUMN）、刪表（DROP TABLE），一執行那些資料就沒了，沒有「復原」可以按，只能靠備份救。改欄位的型別，也可能讓裝不進新格子的舊資料出錯。
這樣會出事
你：「幫我在客戶表加一個統編欄位」

Claude 直接連上正式的資料庫執行。

當下能用。專案裡沒有任何檔案記得這件事，測試用的資料庫也沒有這一欄。
這樣才對
你：「寫成一個 migration 檔，先給我看內容」

1. 你看到要加哪一欄、什麼型別
2. 先在測試用的資料庫跑
3. 沒問題，才套到正式的

檔案留在專案裡，誰來接手都翻得到。
這三種動作，要你本人點頭
刪欄位、刪表、改欄位的型別或名稱。

動手之前先確認兩件事：有備份，而且你知道怎麼還原。確認不了，就先不要做。
跟 Claude 怎麼說
「資料表結構的修改一律寫成 migration 檔，不要直接改正式的資料庫」
「先給我看這個 migration 會做什麼：加哪一欄、什麼型別、舊資料這一欄會是什麼值」
「這個 migration 有沒有會讓資料消失的動作？有的話列出來，等我說可以才執行」
「先在測試用的資料庫跑一次，把結果給我看」

實際怎麼用：先看清楚，再讓它動

第一步：盤點

不管是剛接手別人的專案，還是自己做了三個月，先請 Claude 把現況列出來。這一步只看不改：

先不要改任何東西。列出現在所有的資料表，每張表給我：
1. 它放什麼（一句話）
2. 每個欄位的名稱、型別、白話說明
3. 哪一欄連到哪張表

第二步：五分鐘健檢

清單在手上，拿前面那五個坑一個一個對，再多問一題：每張表都有 id、建立時間、更新時間嗎？看不出來的，直接把題目丟給 Claude 回答。

答不好的那一題，就是下一次該整理的地方。不用一次全改，先知道洞在哪。

還沒開工的話：先找現成的

客戶、合約、付款、預約、訂單，這些表別人已經設計過很多遍。動手之前，照第十一章 技術棧說的先上 GitHub 找同類的專案，再請 Claude 把它們的資料表列出來對照：別人多了哪些欄位、為什麼。不一定要用它們的程式，光看表怎麼切就值得。

之後每一次要改

回到前面那三句：這個東西有沒有地方放了、屬於哪張表、哪些功能要跟著改。它答完、你確認了，再讓它動。

  • 一格只放一種東西；金額不用 float；狀態用一欄 status；刪除做成軟刪除。
  • 查得到的不存，算得出來的不存；留底的是「當時的事實」。
  • 你要會的不是設計資料庫，是看得出它在加第二份。加欄位之前，問那三句。
  • 改結構寫成 migration 檔；會讓資料消失的動作，等你點頭。
所以你要會的是什麼
不是自己設計資料庫，是看得出它在加第二份。

不懂這一章，讓 AI 一直改下去：每一次需求多一欄，同一件事存在好幾個地方，半年後沒有人敢說哪一個數字才對，要整理又怕弄丟資料。

懂了以後，你只要守住一句：「先告訴我這個東西現在放在哪，再告訴我你要動哪張表的哪一欄。」其他的可以交給它寫。
跟 Claude 怎麼說：寫進 CLAUDE.md 的幾條
「每張表都要有 id、created_at、updated_at；表和表之間只用 id 連」
「同一筆資料只存一個地方。查得到的不存，算得出來的不存；要留底的先跟我說理由」
「金額用整數或 numeric，不用 float」
「刪除做成軟刪除，不用 ON DELETE CASCADE」
「加欄位、開新表之前，先回答：現在有沒有地方放了、它屬於哪張表、哪些功能要跟著改」
「結構的修改一律寫成 migration 檔；刪欄位、刪表、改型別要等我說可以」

第十七章

會出事的地方：異步、單一資料來源、耦合

上一章把前端和後端中間那條線畫好了。線畫好，東西還是會壞，而且多半壞在幾個固定的地方。當你的專案從「一頁式網站」長成「多功能系統」，有些觀念會從「聽過就好」變成「不懂就踩坑」。這一章把最常見的三種攤開：順序亂掉、同一份資料存好幾處、改一個壞三個。每一種都對得回前面某一章的邊界。

這三種壞法有一個共同點：剛發生的時候，畫面上看不出來。測試的時候只有你一個人在按、資料只有幾筆、功能剛做好，全部正常。等到兩個人同時按、資料改過幾輪、功能加了半年，才一起冒出來。

壞法 出事長什麼樣 沒守住的邊界
順序亂掉（異步、Race Condition） 舊的搜尋結果蓋掉新的；最後一個座位賣給兩個人 第十四章：誰等誰，是串流程那一塊的事；第十六章：庫存只有後端說了算
同一份資料存好幾處（單一資料來源） 網頁寫 299 元，結帳收 350 元 第十五章：查得到的不存，算得出來的不存
改一個壞三個（耦合） 改登入頁的按鈕，結帳頁跟著壞 第十四章：一塊只做一件事

第一種：異步（Async），三道菜同時做

比喻：餐廳廚房。

你在餐廳點了三道菜：沙拉、牛排、甜點。

同步做法：廚房做完沙拉、端出來，才開始煎牛排；牛排端出來，才開始做甜點。你等到天荒地老。

異步做法：三道菜同時開工。沙拉區切菜、煎台煎牛排、甜點區挖冰淇淋，誰先做好誰先上桌。快很多。

程式的世界也是這樣。同步（synchronous）是一件事做完才做下一件；異步（asynchronous）是幾件事一起開工，誰先完成誰先回報。網頁上查資料、存資料、寄信，幾乎都是異步：送出去之後，不知道什麼時候回來。

畫出來大概長這樣：

同步：一件接一件
查會員資料 2 秒
查訂單紀錄 3 秒
寄通知信 1 秒
總共 2 + 3 + 1 = 6 秒
異步：同時開工
查會員資料 2 秒
查訂單紀錄 3 秒
寄通知信 1 秒
總共 3 秒，等於最慢的那一件。全部到齊，再繼續

看起來異步完勝？大部分情況下異步確實比較快，Claude 也常常這樣寫。麻煩出在先後。

坑一：到的順序亂了

回到同一間餐廳。「誰先做好誰先上桌」會帶來兩種麻煩，第一種是上桌的順序。

你想的順序是沙拉、牛排、最後冰淇淋。但冰淇淋挖一球只要十秒，第一個上桌；牛排要煎十五分鐘，最後才到。等你吃完牛排，冰淇淋已經變成一碗甜湯。

三道菜都沒做錯，錯在上桌的順序沒有人管。

程式裡長這樣：你在搜尋框打「台中」。打到「台」的時候送出一次查詢，打完「台中」又送出一次。沒有人保證哪一個先回來。「台」的結果如果比較晚到，就會把「台中」的結果蓋掉：你明明打的是台中，畫面卻停在「台」開頭的那一長串。

記住一件事就好：做好的順序，不等於你要的順序。先送出去的，不一定先回來。順序重要的時候要講明：誰要等誰、晚到的舊結果要不要丟掉。

坑二：這一步要用上一步的東西

牛排的醬汁，要用煎完牛排的那個鍋底來做。牛排還沒下鍋，鍋底是空的，師傅再厲害也做不出醬汁。

這跟誰快誰慢無關。第二步要用到第一步做出來的東西，所以這兩步不能同時開工。
換成程式：

假設你做了一個「註冊流程」：
1. 在資料庫建立使用者帳號
2. 用這個帳號的編號（ID）去建立預設設定
3. 寄歡迎信給使用者

如果三步同時跑（異步），第二步一開工就要帳號的編號，但帳號還沒建好，哪來的編號？

結果：註冊到一半出錯，因為它找不到一個還不存在的帳號。運氣不好的話，還會留下一個沒有設定的帳號。

判斷方法只有一個問題：這一步需要上一步的結果嗎？需要就排隊，不需要才能同時做。上面的第二、三步都要等第一步；但第二步和第三步彼此不相干，可以一起跑。

對回哪條邊界
第十四章 功能怎麼切裡有一個「店長」，它不算錢、不排版，只管順序。誰等誰、晚到的舊結果丟不丟，就是店長要定的事。這件事沒人講，Claude 多半照最快的寫法：能同時跑的全部同時跑。
跟 Claude 怎麼說
「搜尋框連續打字的時候，只顯示最後一次查詢的結果，比較晚回來的舊結果要丟掉」
「這幾個查詢彼此不相干，可以同時跑，但畫面等全部回來再一起顯示」
「第二步要用到第一步的結果，這兩步照順序做；彼此不相干的才同時跑」

另外還有一種麻煩，不是順序，是兩個人同時搶同一個東西。它有自己的名字。

Race Condition：搶最後一個座位

Race Condition（競爭條件）是異步最經典的問題。想像這個場景：

電影院最後一個座位。小明和小華在各自的手機上訂票，兩個人幾乎同一秒按下「訂票」。系統各查一次：「還有空位嗎？有。」兩個人都訂到了。但實際上只有一個座位，有人到現場沒位子坐。

沒處理 Race Condition
小明查：有 1 個空位 → 訂！
小華查：有 1 個空位 → 訂！

結果：2 個人搶到 1 個座位
有人到現場沒位子坐
有處理 Race Condition
小明查：有 1 個空位 → 鎖住 → 訂！
小華查：座位被鎖 → 等一下⋯⋯
小明完成 → 解鎖 → 空位 = 0
小華查：沒位子了 → 顯示已售完
一個座位只賣一次

「鎖住、解鎖」是工程師的說法（Lock）。落到實際做法，最常見的是把「查還有沒有」和「扣掉一個」併成同一句話，交給資料庫一次做完：

這樣會出事：先查，再扣
小明查：剩 1 個 → 訂
小華查：剩 1 個 → 訂
小明扣一個 → 剩 0
小華扣一個 → 剩 −1

一個座位賣了兩次
這樣才對：查和扣一步做完
小明：「剩 1 個以上就扣一個」→ 成功，剩 0
小華：同一句，前面有人在改，排隊
輪到小華：重看一次，剩 0 → 已售完

一個座位只賣一次

先選一種寫法，再按「兩人同時按訂票」。這只是畫面上的模擬，不會送出任何資料。

剩餘座位1 訂票成功0
小明的手機
    小華的手機

      還沒開始。

      為什麼前端擋不住？小明畫面上那個「剩 1 個」，是他打開頁面那一刻拍的照片，照片不會自己更新。真正的數字只有資料庫知道，所以「查還有沒有」和「扣掉一個」要在資料庫裡一步做完。

      這不用你寫。Supabase 底下是 PostgreSQL，兩個人同時改同一筆資料時，後到的那個會等前一個做完，再重新確認條件還成不成立；把查和扣寫成同一條指令或一個資料庫函式，就吃得到這個保護。Cloudflare D1 也可以把幾條指令包成一批，一起成功，或一起取消。你只要知道要叫它這樣做。

      同一件事做了兩次

      還有一種「同時」：網路慢，客人以為沒按到，又按一次「送出訂單」。後端收到兩張一模一樣的訂單，扣了兩次款。

      解法是每張訂單在送出前就有自己的編號。後端看到同一個編號第二次，回一句「已經收過了」，不再做一次；資料庫也可以設定「這一欄不准重複」，第二筆根本寫不進去。按鈕按下去先變灰，只是讓人少按一次，真正擋住的是後端那一關。

      對回哪條邊界
      第十六章 前後端邊界說，庫存只有後端說了算；第十五章 資料表與欄位說，資料有一個家。搶座位和重複送出，是這兩條加在一起：判斷要在資料的家裡做，不在客人的手機上做。
      跟 Claude 怎麼說
      當你的系統開始有「多人同時操作」的需求時，記得跟 Claude 說：
      「這個功能可能有 race condition。兩個人同時訂最後一個位子，只能有一個成功；查和扣要在資料庫裡一步做完，不要前面查完再送」
      「同一張訂單送兩次，後端只能收一次。用訂單編號擋，按鈕變灰只是輔助」
      「找出專案裡所有『先查、再改』的地方，列給我看哪些可能被兩個人同時做」

      第二種：單一資料來源，全公司只有一本電話簿

      單一資料來源，英文是 Single Source of Truth，縮寫 SSOT。聽起來很哲學，其實超級實用：每一筆資料只住一個地方，別的地方要用，就去那裡問。第十三章 架構拓樸在圖上標過「資料唯一的家」，第十五章 資料表與欄位講過「查得到的不存，算得出來的不存」。這一節看沒做到的時候，出事長什麼樣。

      比喻：電話簿。

      假設公司有三個部門，每個部門各自維護一份員工電話簿。

      小明換了手機號碼，人事部更新了，但業務部和工程部還是舊號碼。
      三個月後，業務部打小明電話打不通，客戶的案子卡住了。

      問題出在哪？同一筆資料存了三份，只更新了一份。

      程式裡也是一模一樣的問題。來看一個常見的例子：

      實際問題：商品價格存了三個地方

      沒有單一資料來源：三份各自為政
      前端 JavaScript：
      const price = 299; // 寫死在程式裡

      後端 API：
      return { price: 350 }; // 上次改了忘記通知前端

      資料庫：
      product.price = 399; // 最新的價格

      結果：客戶看到 299，結帳變 350，
      月底對帳是 399。三個數字都不一樣。
      有單一資料來源：只存一個地方
      資料庫（唯一的家）：
      product.price = 399;

      後端 API：
      return db.getProduct(id); // 去資料庫查

      前端：
      const data = await fetch('/api/product');
      // 顯示後端回傳的價格

      結果：不管在哪裡看，都是 399。
      改一個地方，全部跟著變。

      三份裡沒有一份是「寫錯」的，每一份都是當時改對的。錯在沒有人說過：以哪一份為準。

      原則很簡單：每一筆資料只存在一個地方，其他需要這筆資料的地方，都去那裡查。

      常見的「唯一的家」

      場景 唯一的家 其他地方怎麼做
      商品價格 資料庫 前端、後端都去資料庫查
      使用者權限 後端的權限表 前端只負責顯示，不自己判斷
      設定值（稅率、運費、服務網址） 環境變數／一份設定檔 程式啟動時讀取，不寫死在程式裡
      畫面狀態（購物車裡有什麼、目前選了哪個分頁） 頁面上一個集中存放的地方 各區塊都去那裡讀，不各自記一份

      第二份常常藏在這些地方

      第二份藏在哪 出事的樣子 該以誰為準
      頁面上寫死的價格、方案內容 後台改了價，網頁還是舊的 資料庫
      另外一份 Excel 或 Google 試算表的客戶名單 客人換了電話，業務打的是舊號碼 資料庫；試算表只能是匯出來的抄本
      報表自己存的加總 補登一筆付款，報表的數字沒變 付款紀錄；加總從紀錄算出來
      寫死在好幾個檔案裡的稅率、運費 運費調了，有一頁還在收舊的 一份設定
      頁面自己記住的「這個人是管理員」 已經停權的人，畫面上還看得到管理按鈕 後端的權限資料

      有些第二份是故意的：簽約當天的金額要留底（第十五章），報表為了快另存一份抄本（第十三章）。分辨方法還是那一句：來源改了，這一份該不該跟著變？該變卻沒變的，就是會出事的那一份。故意留的，要寫明「以哪一份為準」，不然半年後沒有人分得出來。

      對回哪條邊界
      第十五章那條「同一筆資料只存一個地方」。Claude 每次只讀它覺得跟這次有關的檔案，這一頁要價格，它就在這一頁寫一份，最快。家在哪裡，要你先講。
      跟 Claude 怎麼說
      「這個資料的家是資料庫，前端不要自己存一份」
      「幫我檢查一下，有沒有同一筆資料被存在多個地方的情況。列出來，說明哪一份該為準」
      「這份試算表是抄本，以資料庫為準。不要讓任何功能去改它」

      第三種：耦合（Coupling），積木 vs 膠水模型

      比喻：積木和膠水。

      想像你蓋了一個模型城堡：

      用積木蓋的（低耦合）：每一塊都是獨立的。你拆掉一棟塔樓，城牆還是好好的。想換一個更酷的塔樓？直接拔掉舊的、插上新的。

      用膠水黏的（高耦合）：所有零件都黏死在一起。你想拆掉一棟塔樓？不好意思，旁邊的城牆、護城河、吊橋全部一起碎掉。

      軟體的世界裡，「耦合」就是指兩個功能之間的依賴程度。依賴越深，耦合越高；依賴越少，耦合越低。第十四章 功能怎麼切講過一開始怎麼切才不會黏。這一節看已經黏起來之後，出事的現場長什麼樣，以及怎麼把它拆開。

      高耦合的痛：改 A 壞 B、C、D

      這是新手最常遇到的地獄場景。下面三個現場都很常見。

      現場一：共用同一段樣式。你跟 Claude 說「幫我改一下登入頁面的按鈕顏色」，結果改完之後：

      • 首頁的上方標題列（header）跑版了
      • 結帳頁面的按鈕消失了
      • 手機版的選單打不開了

      為什麼？因為整站的按鈕共用同一段 CSS，Claude 改的是那一段，不是登入頁那一顆。牽一髮動全身。

      現場二：改了一個欄位的名字。你請它把客戶表的 phone 改叫 mobile。客戶頁正常，但月報表、LINE 通知、匯出功能都直接讀那個欄位，一起壞掉。哪些地方在讀它，沒有人記得。

      現場三：一個檔案裝了所有東西。這是最常見的。

      高耦合：所有東西攪在一起
      一個 app.js 檔案裡面塞了：
      - 登入邏輯
      - 商品列表
      - 購物車計算
      - 寄信功能
      - 金流串接

      改登入 → 購物車壞了
      改金流 → 寄信功能掛了
      全部糾纏在一起，每次都不敢確定沒碰壞別的
      低耦合：功能模組各自獨立
      每個功能獨立一個模組：
      - auth/login.js　　→ 只管登入
      - products/list.js → 只管商品
      - cart/calculate.js → 只管購物車
      - email/send.js　　→ 只管寄信
      - payment/stripe.js → 只管金流

      改登入 → 其他功能不受影響
      改金流 → 寄信功能照樣運作
      改一個，其他檔案沒被打開過

      三個現場有一個共同點：出事的地方，不是你叫它改的地方。所以光看它改的那一處是對的，抓不到。

      怎麼降低耦合

      比喻：部門之間用公文往來。

      公司裡，業務部需要工程部做一個功能。正確做法是寫一張需求單，工程部照單來做。

      錯誤做法是業務部的人直接跑去工程部的桌上翻資料、改東西。工程部根本不知道什麼被改了，下次上線直接出事，也沒人查得出來。

      模組之間的溝通，應該透過講好的窗口，而不是直接伸手進別人的內部。這個窗口，工程師叫它介面（interface）；開給別的系統用的那一種，就是第十二章講的 API。

      降低耦合的三個基本原則：

      1. 功能拆成獨立模組。每個檔案只做一件事。登入歸登入、購物車歸購物車，第十四章那張功能清單就是在定這個。
      2. 模組之間只走講好的窗口。A 模組需要 B 模組的資料？透過 B 開出來的 function 去拿，不要直接去改 B 的內部變數。購物車要知道誰登入了，去問登入那一塊，不要自己去翻它存的東西。
      3. 共用的東西越少越好。就像不要讓所有部門共用一張桌子，每個模組管好自己的資料。共用一段樣式、一個全域變數、一個欄位，每多一個，就多一條看不見的線。真的要共用，讓 Claude 列出有誰在用。

      已經黏在一起了怎麼辦

      不要說「全部重寫」。重寫會把現在能動的東西也一起賭進去。一次拆一塊：先請 Claude 列出黏在一起的地方，挑最常改的那一塊拆出來，拆完把整個流程跑一次，確認結果跟拆之前一樣，再拆下一塊。慢，但每一步都退得回去。

      對回哪條邊界
      第十四章規格裡「不准動哪裡」那一行，加上第十三章那張圖。改之前先問它會動到哪幾塊；答案比你預期的多，就是黏住了。
      跟 Claude 怎麼說
      「改這個之前，先告訴我還有哪些地方用到它。列出來，先不要動手」
      「只改登入頁的這顆按鈕，不要動全站共用的那段樣式」
      「改欄位名字之前，先找出所有讀這個欄位的地方」
      「這個功能跟其他模組耦合太高了，幫我拆成獨立的 module」
      「我不想改 A 的時候影響到 B，幫我用 interface 把它們分開」
      「這個檔案太大了，幫我按功能拆分。一次只拆一塊，拆完跑一次，確認結果跟拆之前一樣」

      這一節只講到為什麼要拆。怎麼切功能看第十四章 功能怎麼切，整體怎麼連看第十三章 架構拓樸，資料怎麼放看第十五章 資料表與欄位。

      三種壞法，同一個根

      回頭看，三種都是同一件事：Claude 每次只看你眼前講的那一句，挑最近的路。同時跑最快，就同時跑；這一頁要價格，就在這一頁寫一份；要改按鈕，就改那段共用的樣式。每一次都修好了，合起來就是第一章說的越改越纏。

      所以這一章不是要你學會修。是讓你在它動手之前，問得出那一句：「這樣做，會不會跟別的東西撞在一起？」

      本章術語表

      這些詞會出現在 Claude 的回覆裡。看得懂就好，不用背。

      術語 白話
      同步／異步
      Sync／Async      		 一件做完才做下一件／幾件同時開工，誰先好誰先回
      Race Condition
      競爭條件      		 兩個人同時搶同一個東西，結果看誰剛好快一點
      鎖
      Lock      		 有人在改的時候，其他人先排隊
      重複送出 同一件事被送了兩次。後端要認得出「這張已經收過」
      單一資料來源
      SSOT      		 每一筆資料只住一個地方，別處要用就去問它
      耦合
      Coupling      		 功能黏在一起的程度，第十四章講過
      介面
      Interface      		 塊和塊之間講好的窗口，像部門之間的需求單

      這章帶走什麼

      • 先送出去的，不一定先回來。要用上一步結果的，排隊做；搶同一個東西的，查和扣在資料庫裡一步做完。
      • 同一筆資料只住一個家。第二份不是不能有，但要寫明以誰為準。
      • 出事的地方，常常不是叫它改的地方。改之前先問會動到哪裡；已經黏住了，一次拆一塊。
      • 三種壞法都是邊界沒講。不是自己寫，是在它動手之前說清楚：這件事放哪一塊，這次動到哪裡為止。
      跟 Claude 怎麼說：寫進 CLAUDE.md 的三條
      「會被兩個人同時改的東西（庫存、座位、訂單），查和改要在資料庫裡一步做完；同一張訂單只能收一次」
      「同一筆資料只存一個地方；要另存一份，先跟我說理由，並寫明以哪一份為準」
      「改任何東西之前，先列出還有哪些地方用到它；會動到別的功能，先停下來問我」

你缺什麼知識：路徑、網域、網址

根目錄、路徑、前後端、網域、路由。這些不是「工程師才需要知道的東西」，而是你跟 AI 溝通時的基本語言。少了這些字彙，每一句話都在燒 Token。

  2. 前端與後端：用餐區和廚房
  3. 網域：網站的門牌號碼

上一章講順序：先做 Demo、列邊界清單、看計畫，再一次做一塊。可是計畫裡寫著「改 pages/about.html」「這段放後端」「加一個子網域」，你得先看得懂這些字，才知道它要動哪裡。

這章補最基本的幾個字。你不需要會寫，只要認得、說得出名字。

根目錄與路徑：你家的地址

比喻：你家的地址。

「根目錄」就是你家的大門。「路徑」就是從大門走到廚房怎麼走。

你不會跟外送員說「就那個有桌子的地方」，你會說「三樓左轉第二間」。
跟 AI 講話也一樣，你得告訴它「檔案在哪裡」，而不是「就那個檔案」。

什麼是根目錄？

根目錄（Root Directory）就是你的專案的「家」，也就是專案資料夾。所有東西都住在這裡面。

在 Mac 上，一個典型的專案路徑長這樣：

/Users/你的名字/Desktop/my-project/

把這串路徑拆開來看：

片段 意思 比喻
/ 整台電腦的最頂層 國家
Users/ 所有使用者的資料夾 城市
你的名字/ 你自己的帳號空間 你住的區
Desktop/ 桌面 你家那條街
my-project/ 你的專案資料夾（根目錄） 你家

所以當 AI 問你「根目錄在哪？」，它就是在問：「你家地址是什麼？」

絕對路徑 vs 相對路徑

絕對路徑 = 從國家開始講的完整地址
「台灣 / 台北市 / 信義區 / 信義路 / 100 號 / 3 樓」

相對路徑 = 從你現在站的位置怎麼走
「左轉 → 走到底 → 第二間」

用電腦的語言來說：

絕對路徑（從最頂層開始）
/Users/你的名字/Desktop/my-project/pages/about.html

不管你人在哪裡，這個地址都能找到它。

相對路徑（從你現在的位置）
./pages/about.html

「從我現在站的地方，走進 pages 資料夾，找到 about.html」

小提示
./ 代表「現在這裡」，../ 代表「往上走一層（回到上一個資料夾）」。
就像你在三樓說「往樓下走一層」就是 ../。

跟 Claude 溝通的範例

模糊的說法
「幫我改那個 HTML 檔案」
精準的說法
「幫我改 pages/about.html
裡面最上面那個標題的文字」

不用講到第幾行。行號你要另外開檔案才看得到，而且改一次就跑掉；講「哪個檔案、哪一塊」就夠了。

不用自己拼路徑
Mac 的 Finder：選好你要的檔案或資料夾，按 Option + Command + C，就能直接複製完整路徑。也可以按右鍵，同時按住 Option，選單裡會出現「將…拷貝為路徑名稱」。

然後回到 Claude Code，貼上路徑，直接說：
「我的專案在 /Users/你的名字/Desktop/my-project/，幫我修改裡面的 index.html」

Claude Code 裡：打一個 @，會跳出檔案清單讓你挑，挑好的檔案會直接帶進對話。

這兩招可以省掉你手動拼路徑的痛苦，也避免打錯字浪費 Token。

前端與後端：餐廳的用餐區和廚房

前端 = 餐廳的用餐區（客人看到的一切：菜單、裝潢、桌椅）

後端 = 餐廳的廚房（客人看不到的，但出餐全靠它：廚師、爐子、收銀）

資料庫 = 倉庫（食材和帳本都收在這裡，需要的時候廚房去拿）
術語 餐廳比喻 實際是什麼 常見技術 這本書用的
前端 Frontend 用餐區、菜單、裝潢 你在瀏覽器看到的一切：按鈕、文字、動畫、表單 HTML、CSS、JavaScript；也有人用 React、Vue（要先打包才能上線） HTML、CSS、JS 寫的純靜態頁面，改完直接上傳 Cloudflare
後端 Backend 廚房、廚師、收銀台 客人碰不到的那一段：登入驗證、付款、計算 Node.js、Python、Java、Go 有人按鈴才醒來辦事的小函式（Cloudflare Workers、Supabase Edge Functions），或資料庫本身的存取規則
資料庫 Database 倉庫 存放資料的地方：使用者帳號、訂單紀錄、文章 PostgreSQL、MySQL、SQLite、MongoDB Supabase（底下是 PostgreSQL）或 Cloudflare D1（SQLite 的寫法）
API 服務生 前端跟後端溝通的窗口（第十二章會詳細講） REST API、GraphQL Supabase 替你的資料表產生的，或小函式開出來的

這本書為什麼選這一組、不從 React、Vue 這類要打包的做法開始，在第十一章 技術棧。

當你跟 AI 說「那個東西壞了」，它需要知道是「用餐區壞了」（前端 bug）還是「廚房壞了」（後端 bug）。差別在哪？

前端的問題（用餐區）
按鈕按了沒反應
文字跑版、重疊
手機上看排版亂掉
動畫卡卡的
後端的問題（廚房）
登入之後一直跳回登入頁
資料存了但下次打開不見了
付款成功但訂單沒建立
打開頁面要等很久資料才出來
為什麼要分這麼清楚？
因為前端和後端的「修理方法」完全不同。
你跟 AI 說「按鈕按了沒反應」，它得知道是按鈕本身壞了（前端 JavaScript），還是按鈕送出去的請求沒回來（後端 API）。
講對方向，AI 一次就修到點上；講錯方向，來回好幾輪才找到問題。

分清楚還有第二個用處：決定一件事該交給哪一邊做。菜單在客人手上，看得到、也塗改得到；廚房客人進不去。

  • 菜單上的價格可以印給客人看，但結帳金額要店裡自己算，不能客人說多少就收多少。
  • 「沒填就標紅」放前端就好，客人當場知道要補；但資料真的存進去之前，後端還要再檢查一次。

現在先記一句：跟錢和權限有關的，最後都要後端說了算。

頁面直接連資料庫，可以嗎？
用 Supabase 的話可以，這本書推薦的組合就是這樣做。前提是每一張表都打開存取規則（RLS，Row Level Security），由資料庫自己決定誰能讀、誰能改哪幾筆。規則就是這時候的「廚房」：客人拿到菜單，也進不了倉庫。

Supabase 官方文件寫得很清楚：對外開放的表，每一張都要開 RLS；沒開的表，等於誰都能讀能改。新建的表還要先授權（grant）才會開放，不只是開 RLS，做法見第九章 資料庫。跟 Claude 說：「每一張新表都要開 RLS，寫好規則再給我看。」

前端、後端、資料庫整體怎麼連，第十三章 架構拓樸會畫成一張圖給你看。專案長大以後這條線會越來越難分，什麼可以在前面用 JS 做、什麼一定要放後面，第十六章 前後端邊界有更多例子。

網域（Domain Name）：網站的門牌號碼

網域就是網站的門牌號碼。

google.com 就是 Google 的地址，就像「信義路 100 號」是某棟大樓的地址。
你不用記住大樓的 GPS 座標（IP 位址），只要記門牌（網域）就好。

網域的結構

把 mail.google.com 拆開來看：

部分 叫什麼 比喻 例子
.com 頂級網域 TLD 哪一區（商業區 / 政府區） .com / .org / .tw / .io
google 主網域 哪棟大樓 google / facebook / example
mail 子網域 Subdomain 大樓裡的哪個部門 mail / docs / blog / api
mail.google.com
子網域　主網域　頂級網域

更多例子：
docs.google.com　　→ Google 的文件部門
api.example.com　 → example 的 API 入口
blog.mysite.com　　→ 我的網站的部落格
你可以這樣跟 Claude 說
「網站是 a-studio.example，我想加一個子網域 blog.a-studio.example 放部落格。」
「API 放在 api.a-studio.example，前端放在 app.a-studio.example。」

這裡先認得門牌怎麼讀。網域要去哪裡買、買了怎麼接到你的網站上，第八章 網域會帶你實際買一個、接上去。

路由、前綴與後綴：網站裡的走廊

路由（Route）= 網站的走廊

路由就是網站裡面的門牌。

網域告訴你「哪棟大樓」，路由告訴你「大樓裡面走到哪」。

example.com/products → 走到商品區
example.com/about → 走到「關於我們」
example.com/products/123 → 走到商品區，找編號 123 的商品
https://example.com/products/123

https://　　　　→ 通訊協定（怎麼連線的，先不管）
example.com　　 → 網域（哪棟大樓）
/products/　　　→ 路由第一層（商品區）
123　　　　　　 → 路由第二層（編號 123 的商品）

純靜態網站的路由很直白：一個資料夾放一個 index.html，資料夾的名字就是網址。像這本書，/chapter5/ 這一頁就是 chapter5 資料夾裡的 index.html。

前綴（Prefix）和後綴（Suffix）

術語 白話 在哪裡看到 例子
前綴 Prefix 加在前面的標記 子網域、API 路徑開頭 api.example.com 的 api
example.com/v2/users 的 v2
後綴 Suffix 加在後面的標記 檔案的副檔名 index.html / style.css / app.js

常見副檔名（後綴）對照表

副檔名 全名 白話 類比
.html HyperText Markup Language 網頁的骨架和文字 像 Word 的 .doc
.css Cascading Style Sheets 網頁的衣服（顏色、大小、排版） 像 PowerPoint 的主題
.js JavaScript 網頁的動作（按了會怎樣、互動、邏輯） 像 Excel 的巨集
.json JavaScript Object Notation 資料的格式（像表格一樣存資料） 像 CSV 但更有結構
.sql Structured Query Language 對資料庫下的指令，例如建表、查資料 像給倉庫的作業單
.ts TypeScript JavaScript 的加強版（多了類型檢查）。瀏覽器不能直接跑，要先轉成 .js 像 JS 穿了防護衣
.env Environment 放密碼、金鑰的檔案 像保險箱，不能公開
.md Markdown 輕量格式的文件，CLAUDE.md 就是 像精簡版的 Word
.yaml / .yml YAML Ain't Markup Language 設定檔 像填寫表格

這本書推薦的純靜態頁面，平常只會碰到 .html、.css、.js，加上資料庫的 .sql 和 Claude Code 的 .md。看到一堆 .ts、.tsx，多半是要打包的專案。

注意
.env 檔案裡存的是密碼和 API 金鑰，絕對不能上傳到 GitHub。
這就像你不會把保險箱密碼寫在大門上一樣。怎麼處理，見附錄 常見問題。

完整拆解一個網址

把你每天都在看的網址完整拆開：

https://api.example.com/v2/products/123?color=red

https://　　　 → 通訊協定（加密連線）
api　　　　　　→ 子網域（前綴）：這是 API 入口（程式之間講話的窗口）
example.com　　→ 主網域：哪棟大樓
/v2　　　　　　→ 路由前綴：API 第二版
/products　　　 → 路由：商品區
/123　　　　　　→ 路由參數：編號 123 的商品
?color=red　　　→ 查詢參數：只要紅色的

術語總對照表

術語 白話 比喻
根目錄 Root Directory 專案的最上層資料夾 你家大門
路徑 Path 檔案在電腦裡的位置 從大門走到廚房的路線
絕對路徑 從最頂層開始的完整位置 完整地址（含國家、城市）
相對路徑 從現在位置出發的位置 「左轉第二間」
前端 Frontend 使用者看到的畫面 餐廳用餐區
後端 Backend 客人碰不到、處理邏輯的那一段 餐廳廚房
資料庫 Database 儲存資料的地方 倉庫
API 前端和後端講話的窗口 服務生
網域 Domain 網站地址 大樓門牌
子網域 Subdomain 主網域底下的分區 大樓裡的部門
路由 Route 網站裡面的頁面路徑 大樓裡的走廊
查詢參數 Query 網址 ? 後面的條件 跟櫃檯說「只要紅色的」
前綴 Prefix 加在前面的標記 路名前面的「北」「南」
後綴 Suffix 加在後面的標記（副檔名） .doc = Word，.pdf = PDF

更多術語，用到再查術語字典。

這章帶走什麼

本章重點
你不需要會寫這些東西，但你需要認得它們、說得出名字。
當你能說「請幫我改 css/style.css 裡 Header 導覽列的顏色」，
而不是「幫我改上面那一條的顏色」，你跟 AI 的溝通效率立刻翻倍。
  1. 說檔案，要說在哪裡。給路徑，或在 Claude Code 裡打 @ 挑檔案。
  2. 壞了，先分是哪一邊。畫面的問題多半在前端，存不進、登不進、錢不對多半在後端。
  3. 跟錢和權限有關的，後端說了算。頁面直接連 Supabase 時，把關的是每張表的 RLS 規則。
  4. 網址拆得開。子網域、主網域、路由、查詢參數，各自是哪一段。
  5. .env 不上 GitHub。

名字叫得出來了，下一步是把畫面上看到的東西講清楚：哪一塊、哪個樣子、改成什麼。下一章 描述力。

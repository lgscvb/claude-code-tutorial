第一章

為什麼要懂：能改能修，靠的是知道邊界

首頁講了一句話：做出來以後，還要能改、能修。這一章把它講開：AI 為什麼會越改越亂、你到底要懂到什麼程度，以及這本書接下來每一章，各自守的是哪一條邊界。

做出來，只是第一天

現在跟 AI 說一句「幫我做一個報價單網站」，它真的做得出來。畫面有了，按鈕會動，資料存得進去。很多人做到這裡，就覺得自己會了。

麻煩在後面。工具做出來是要給人用的。A 設計工作室的業務開始用你做的報價單，第二個禮拜就會來找你：

  • 「可以加一個折扣欄嗎？」
  • 「客戶要分兩期付，報價單能不能拆兩張？」
  • 「上個月那張報價怎麼找不到了？」

每一件都是小事，每一件 AI 也都會幫你改好。問題是改了十次、二十次以後，這個工具還是不是你看得懂、改得動的樣子。

不是說下指令做一個網站，是要能改能修。

這本書就是在講這件事。下指令做出東西，是第一天。後面每一天的改和修，才是工具能不能一直用下去的關鍵。

AI 會改會修，但它會一直改

Claude 很會改，也很會修。你說哪裡壞了，它就去修；你說要加什麼，它就去加。但它每次只處理你眼前講的那一件事。

前端改一點，後端改一點，資料表加一個欄位，再多開一張表。每一步單獨看都合理。改到後面，東西全部纏在一起：動一個地方，壞到另一個地方。最後沒有人能維護，連 AI 自己也越改越亂。

看一個例子。假設你做了一個有折扣的結帳功能，接下來三個禮拜，前後跟 Claude 講了五次：

  1. 第 1 天
    你：「結帳頁要顯示折扣後的金額」它在前端算了一次。
  2. 第 5 天
    你：「訂單明細的金額跟結帳頁不一樣」它在後端也算了一次。
  3. 第 9 天
    你：「加一個會員價」訂單表多了一個欄位，前端多了一段判斷。
  4. 第 14 天
    你：「報表的營收對不起來」報表自己又算了一次。
  5. 第 20 天
    你：「九折改成八五折」要改四個地方。漏掉一個，數字又對不起來。

每一步都修好了。合起來，同一個「價格」有四套算法，散在前端、後端、資料表和報表裡。本來該各管各的東西黏在一起，工程師叫它「耦合」。怎麼切開看第十四章 功能怎麼切，出事的情境看第十七章 會出事的地方。

這不是 Claude 哪一次做錯。是從頭到尾沒有人說過「價格只有後端能算」。它不知道線在哪，就哪裡近改哪裡。

所以能力是知道邊界

你不用自己寫程式。你要會的是知道邊界。邊界講的是兩件事：

  • 這件事該放在哪一塊。價格放後端算，畫面放前端顯示，客戶資料放在客戶那張表。
  • 這次可以動到哪裡為止。說好只改報價單的畫面，就不准順手動到資料表。
像請師傅來裝潢。你不用自己砌牆，但要知道哪一面是承重牆。師傅說「這面順便敲掉比較快」的時候，你才說得出「這面不能動」。

邊界裡面有一條特別難守：前端和後端中間那條線。什麼可以放在頁面上用 JS 做，什麼一定要放在後面，這個判斷你要會。但這條線不可能百分之百字面上乾淨：有些檢查前後各做一次，有些東西本來就設計成放在前面用。第十六章 前後端邊界會一條一條講。

正因為畫不到百分之百乾淨，沒辦法丟一條死規則給 AI 就不管，得有人每次看一眼。那個人就是你。

所以你要會的是什麼
不是自己寫，是知道邊界在哪。

程式可以交給 Claude 寫。但「金額、折扣、庫存、權限、金鑰，只有後端說了算」這種清單要你來定，而且要在它動手之前講。

只講一次不夠，換一個新對話它不會記得。把清單寫進專案的 CLAUDE.md（給 Claude 看的專案說明檔，第十章 Claude Code 怎麼用會講），它每次開新對話都會先讀進去。官方文件也寫明，這份檔對它來說是參考，不是強制規則，所以改完還是要再問一句。範例在本章最後。

要做到什麼程度

這本書的目標是：能做出別人可以用的工具，或帶團隊導入。不是讓你變成工程師。

不是給 AI 做，至少要了解 function 功能，還有架構拓樸、SQL 設計、欄位。

這句話拆開來，是三個程度：

  1. 看得懂

    Claude 說要改哪些檔案、要加哪個欄位、資料從哪裡流到哪裡，你讀得懂它在講什麼。不用看懂每一行程式碼，要看懂它的計畫。

  2. 會判斷

    它給你兩種做法，你分得出哪一種以後比較難改。例如「在訂單表多加一個欄位」和「另外開一張表」，差在哪裡、各自會影響到誰。

  3. 知道邊界

    動手之前，你說得出「這次只動這裡，那裡不准碰」；改完之後，你問得出「有沒有動到不該動的地方」。

不用會的：自己從頭寫程式、背語法、記一堆指令參數。這些 Claude 做得比你快。

做給自己用，和做給別人用

做給自己用的小工具，壞了自己修，資料亂了自己認。做給別人用就不一樣：B 咖啡店的店長每天早上靠它看訂單，它一壞，有人在等；它算錯，有人會少收錢。

所以「別人可以用」的標準不是做出來，是三個月後還有人敢改它。改一個折扣，不會讓報表跟著錯；加一個欄位，不會讓舊資料全部對不起來。

帶團隊導入，你是定邊界的人

一個人用 AI，亂掉的是一個專案。一個團隊五個人各自跟 AI 講話，如果沒有人先定好邊界，五個人的 AI 會往五個方向改。

帶團隊導入的人，不用每一行都看。你要定的是：用什麼技術、資料放哪裡、哪些地方誰都不准讓 AI 亂動。這些寫清楚了，大家才是在同一棟房子裡各自裝修，而不是各自加蓋。

動手可以全丟，邊界不行

第十章會講到，你在電腦上的工作，幾乎 99% 都可以丟給它自己處理。這句話跟這一章不衝突。丟給它的是動手：打字、跑指令、改檔案、查資料。做到哪裡為止、哪裡不准碰，還是你定。

入門照樣要懂

怎麼下指令、學術語，那是入門，照樣要懂。你說不出東西叫什麼，連「這次只改報價單的畫面，不要動資料表」都講不清楚，邊界也就無從守起。

首頁那段 8 輪對 1 輪的對話就是例子：差別不在聰不聰明，在講不講得出名字。入門放在第二章到第六章，忘了的詞翻術語字典。

但現在的重點已經不只是 prompt（給 AI 的指令），是上面那一層：技術棧、架構拓樸。技術棧是你用哪些工具和服務組成這個東西，架構拓樸是這些東西彼此怎麼連。這兩樣看懂了，你才知道一句指令下去，會動到哪幾塊。

這本書怎麼排

十八章加兩個附錄，一共 20 頁，分成六段。順序照你實際會遇到的先後排，每一章守一條邊界：

開頭第一章

  • 第一章 為什麼要懂（就是這一章）邊界是什麼、要懂到什麼程度，和整本書怎麼排。

入門第二到六章

  • 第二章 LLM 本質邊界：它做得到什麼、一次記得多少。對話拉太長，前面講的它會顧不到。
  • 第三章 下指令邊界：你要的，和你不要的。講得出「不要動什麼」，AI 才不會順手改。
  • 第四章 工作流程邊界：先看再做。先做 Demo、看著它確認範圍，規劃好了才正式動手。
  • 第五章 基本知識邊界：東西在哪裡。根目錄、路徑、前端後端、網域，說得出位置，才說得出「只動這裡」。
  • 第六章 描述力邊界：畫面上的哪一塊。講得出元件的名字，AI 才改得到對的地方，不會整頁重做。

動手做第七到九章

  • 第七章 部署邊界：你電腦上的，和網路上的。改完要上傳，別人才看得到；選改完直接上傳、不用打包的做法。
  • 第八章 網域邊界：網址和網站是兩件事。網址買在哪、指向哪裡，分清楚了才不會一動就整站連不上。
  • 第九章 資料庫邊界：資料住在哪裡。頁面可以重做，資料不行；資料庫先開好，資料才有固定的家。

工具第十章

  • 第十章 Claude Code 怎麼用邊界：它能碰你電腦上的什麼。哪些讓它自己做，哪些要它先問你。

判斷第十一到十七章

  • 第十一章 技術棧邊界：用現成的，還是自己做。選不用打包、改完直接上傳的做法；動手前先上 GitHub 找有沒有現成的。
  • 第十二章 API邊界：前端和後端之間怎麼講話。要資料、交資料、對方怎麼回，都有固定的講法。
  • 第十三章 架構拓樸邊界：系統裡塊和塊之間。先畫出來，才指得出這次改動會碰到哪幾塊。
  • 第十四章 功能怎麼切邊界：一個功能管到哪裡。一塊只做一件事，改一條折扣規則不用動好幾個檔案。
  • 第十五章 資料表與欄位邊界：資料住在哪張表、哪個欄位。加欄位、開新表之前先想清楚，資料的家蓋歪了最難改。
  • 第十六章 前後端邊界邊界：什麼放前面，什麼一定要放後面。線畫不到百分之百乾淨，但要知道它在哪。
  • 第十七章 會出事的地方邊界沒守住時，最常見的三種壞法：順序亂掉、同一份資料存好幾處、改一個壞三個。

收尾第十八章、兩個附錄

  • 第十八章 其他工具做影片、管筆記這些事，怎麼交給 Claude Code。
  • 附錄 常見問題錯誤訊息、設定檔、版控卡住的時候先來查。
  • 附錄 術語字典書裡出現的詞，一句白話講清楚，忘了回來查。

為什麼是這個順序：先會講，你才聽得懂 Claude 回你什麼。接著親手把東西放上網、接上網址、存進資料。然後認識每天要一起工作的 Claude Code。最後才是判斷：會選材料、會畫圖、會切功能、會放資料，你才知道線該畫在哪。線畫好了，才談得上守。

為什麼動手做放在判斷前面

先親手把東西放上網、接網址、存資料，後面講邊界才有感覺。

部署、買網域、資料庫，很多人從來沒碰過。沒碰過，「前端」「後端」就只是兩個詞。等你自己把頁面傳上 Cloudflare、把網址接上去、在 Supabase 看到第一筆存進去的資料，你就知道頁面在一個地方、資料在另一個地方，中間隔著一條線。

有了這個經驗，後面講「這段一定要放後面」「這個欄位不要亂加」，你腦中有一個真的東西可以對照。反過來，先學一堆判斷才動手，規則記得住，卻不知道要用在哪裡。

前後端那條線放到第十六章才講，也是同一個道理：它要用到前面每一章。部署時你看過頁面放在哪，資料庫那章你看過資料存在哪；在架構圖上它是一條連線，切功能時它是一道分界，資料表的存取規則也貼著它。前面沒看過，到這裡只會背規則，不會判斷。

這章帶走什麼

  • 下指令做出東西是第一天。工具要給別人用，重點是之後還能改、還能修。
  • AI 會改會修，但每次只看眼前那件事。沒有人定邊界，它會一路改到纏在一起。
  • 邊界是兩件事：這件事放哪一塊，這次可以動到哪裡為止。
  • 你要做到的是看得懂、會判斷、知道邊界，不是自己寫程式。
  • 前後端那條線畫不到百分之百乾淨，所以要有人每次看一眼。
  • 這本書的順序是先會講、再親手做一次、最後學判斷。做過一次，講邊界才有東西可以對照。
跟 Claude 怎麼說
動手之前
「這次只改報價單的畫面，不要動資料表，也不要動後端」
「先列給我看：這次會動到哪些檔案、要不要加欄位或開新表。我確認了你再改」
「如果一定要動到別的地方，先停下來，告訴我要動哪裡、為什麼」

改完之後
「這次動了哪些檔案？有沒有超出我說的範圍？」
「同一個計算有沒有出現在兩個地方？有的話留後端那份」

要它下次還記得
「把『金額、折扣、庫存、權限只能後端決定』寫進這個專案的 CLAUDE.md」
